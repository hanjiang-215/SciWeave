# TerminusDB 与 SQLite 正式化一致性及失败恢复规则

在 Mapping、Wiki 与 SQLite 治理模型确定后，收敛跨存储引用、正式化事务边界和失败恢复语义。

## Design

正式化采用“先确认 TerminusDB 精确图 Commit，再以 SQLite 本地激活单元生效”的领域协议：Project Owner 批准是必要条件但不代表成功；TerminusDB Commit 写入并读回通过后，SQLite 在同一业务原子单元内创建 Formal MappingRevision、比较并切换 `current_formal_revision_id`、写入 `succeeded` 结果并完成 Proposal/Merge Request 状态收敛。该 SQLite 激活提交是唯一生效点。

一次正式化操作有稳定的 `formalization_operation_id`；每次尝试有独立的 FormalizationResult 和递增的 `attempt_number`。TerminusDB Commit 已确认而 SQLite 未能确认时复用原操作和精确 Commit；激活结果未知时显式进入 `reconciliation_required` 并通过读回对账，不盲目重复创建版本。未激活 Commit 保留为不可查询历史，不要求物理回滚。正式查询以 SQLite 当前指针和成功治理记录确定已激活版本，以该 Formal MappingRevision 精确引用的 TerminusDB Commit 作为图内容；两侧无法匹配或 Commit 不可读时明确返回不可用/需对账，不返回候选、不静默回退。

完整状态、失败场景、幂等、查询和审计语义见 [`Research Mapping 跨存储正式化一致性与失败恢复设计`](../docs/superpowers/specs/2026-10-19-research-mapping-cross-storage-formalization-consistency-and-recovery-design.md)。本票不规定具体事务实现、API、队列或部署技术。

## Question

TerminusDB 持有完整候选/正式状态、SQLite 持有治理元数据时，如何保证二者关联一致且审计可追溯？请决定正式化的业务成功条件、提交顺序/确认边界、部分失败后的可见状态、重试或补偿规则，以及查询在两侧状态不一致时采用的权威版本。

## Notes

本票只讨论产品和领域一致性语义；不规定具体事务实现、API 或队列技术。Mapping、Wiki 和 SQLite 字段模型前置已完成。
