# 中央 Worker 以独立子进程运行：派发方只传执行标识

中央侧的 Worker 有两种跑法，两种都不对：

- `gateway/mcp` 用 `multiprocessing.get_context("spawn").Process` 把一个运行时对象当参数传过去。这要求整个运行时对象可 pickle，把「Worker 是什么」绑在了调用方的内存布局上。
- `gateway/subscriber` 直接在自己的进程里内联跑模型（`worker_runner._execute`），一轮 loop 跑多久，订阅循环就阻塞多久。

端侧的形状是：派发方只传执行标识与配置（命令行参数或环境变量），Worker 自己构造运行时；派发方在派发**之前**提交事务，Worker 在自己的连接上读那条记录；超时与失败由派发方判定，不由子进程自报。

这一片把中央侧改成同形状。规格见 `docs/superpowers/specs/2026-10-28-centre-agent-runtime-template-port-design.md` 的「Worker 派发用显式子进程，不用 multiprocessing」。

## Acceptance Criteria

- [ ] 存在一个能以执行标识为唯一入参、独立启动并退出的 Worker 入口（`worker` 子项目现在只有一个校验配置就退出的 `cli.py`，它不是 loop）
- [ ] 派发方在启动子进程之前提交事务；子进程在自己的连接上读执行记录
- [ ] 子进程超时与失败由派发方判定，写回执行记录与审计事件
- [ ] 订阅循环不因一轮 loop 的长度而阻塞（内联跑法被替换）
- [ ] 有测试真的启动一个子进程，读它的退出码，而不是 mock 掉派发
- [ ] 派发失败时执行记录留在可重试的状态，不是静默丢弃
