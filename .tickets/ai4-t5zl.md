# Research Mapping TaskNode 与 Dependency Edge 持久化字段模型

基于已关闭的 Research Mapping 节点/依赖边字段模型和治理规则，将产品领域概念映射为可持久化的具体对象模型。

## Design

书面规格：[`docs/superpowers/specs/2026-10-19-research-mapping-content-persistence-model-design.md`](../docs/superpowers/specs/2026-10-19-research-mapping-content-persistence-model-design.md)。以下是领域字段和关系，不规定 TerminusDB Schema/DDL、ORM、API 或代码结构。

### 存储职责

- Research Mapping Store（TerminusDB）保存不可变的 TaskNode/DependencyEdge 版本正文、端点关系和候选/正式图快照。
- Mapping 治理记录保存 `proposal_id`、`base_formal_revision_id`、`formal_revision_id`、candidate/formal branch 与精确 Commit 关联、审核和审计事实；不复制图正文。
- `Formal MappingRevision` 是产品层版本身份，不等于 TerminusDB Commit。Commit 只表示存储变化，只有和 Project Owner 批准事件及 Formal MappingRevision 成功关联后才可进入正式查询。
- 运行状态、Execution Record、失败详情和结果正文不进入图对象；跨 LLM-Wiki 的引用只保留带领域语义的精确版本弱引用。

### TaskNode 字段

稳定字段为 `mapping_domain_id`、`logical_id`、`version_id`、`title`、`objective`、`scope`、`acceptance_criteria`、`expected_outputs`、`input_refs`、`required_evidence`、`resource_refs`、`task_owner_id`、`executor_refs`、`human_decision_points`、`lifecycle_state`、`proposal_id`、`base_formal_revision_id`、`formal_revision_id`、`derived_from_version_id`、`supersedes_version_id`、`restores_version_id`、`created_by`、`created_at` 和 `source_submission_id`。

- `logical_id` 稳定且不可复用，`version_id` 标识不可变版本；内容字段不能原地修改。
- `title`、`objective`、`scope`、`acceptance_criteria` 和 `expected_outputs` 是任务定义；资源和输入只保存精确版本引用，不嵌入正文。
- `task_owner_id` 是结果接纳和任务变更审核责任人；正式调度前必须能解析执行主体或人工接管路径。
- `lifecycle_state` 只使用 `candidate`、`formal`、`superseded`、`rejected`、`invalidated`。候选必须有 Proposal 和 Formal 基准，正式版本必须有 Formal MappingRevision；运行中的 `ready`/`blocked`/`awaiting_acceptance` 属于运行投影。

### DependencyEdge 字段

稳定字段为 `mapping_domain_id`、`logical_id`、`version_id`、`source_node_version_ref`、`target_node_version_ref`、`dependency_kind`、`required_outputs`、`activation_condition`、`alternative_group_id`、`blocks_until`、`route_change_trigger`、`lifecycle_state`、`proposal_id`、`base_formal_revision_id`、`formal_revision_id`、`derived_from_version_id`、`supersedes_version_id`、`created_by`、`created_at` 和 `source_submission_id`。

- 边方向固定为“前置任务 → 依赖该任务的任务”；两个端点必须精确指向同一 Mapping 域内的 TaskNode 版本，禁止只指向逻辑 ID。
- `dependency_kind` 至少为 `information`、`blocking`、`conditional`、`alternative`；替代边必须有 `alternative_group_id` 和可判定激活条件。
- 关系方向、输出要求、阻塞语义和路线触发条件变化都创建新边版本；正式调度使用的 blocking 子图不得形成无法满足的环。
- 边不保存执行日志、错误详情、资源正文或结果摘要。

### Formal MappingRevision 关系

`FormalMappingRevision` 记录 `formal_revision_id`、`mapping_domain_id`、`terminus_store_id`、`formal_branch_id`、`formal_commit_hash`、`base_formal_revision_id`、`source_proposal_id`、`approval_audit_event_id`、`published_by` 和 `published_at`。TaskNode/DependencyEdge 只通过 `formal_revision_id` 进入正式快照，Commit hash 不在每个图对象中重复保存。

### 场景检查

- 新增任务/边先作为候选版本写入候选分支；批准后才关联新的 Formal MappingRevision。
- 修改目标、完成条件或依赖语义保留旧版本，并创建新版本和来源/替代关系；旧正式版本在候选批准前继续有效。
- 普通执行失败只写 Execution Record/MCP Submission，不改图对象；改变研究路线才进入 Mapping Proposal。
- 候选驳回、冲突或过期的版本保留只读审计，不进入 Formal Query 或正式调度。

## Question

Research Mapping 的 TaskNode、Dependency Edge、版本和 Formal MappingRevision 在 TerminusDB 中分别需要哪些具体字段、标识和关系？请明确：

- TaskNode 与 Dependency Edge 的稳定逻辑身份、不可变版本身份及来源/替代关系；
- 节点内容、依赖语义和运行投影哪些属于持久化领域数据，哪些不应存入图对象；
- candidate/formal 版本如何关联到 Proposal、Formal MappingRevision 和底层 TerminusDB Commit；
- 字段约束、必填性、引用完整性与版本不变量。

## Answer

Research Mapping 采用“不可变图对象版本 + 治理记录关联正式版本”的持久化模型：TaskNode 只保存任务定义，DependencyEdge 只保存精确节点版本之间的依赖语义；Candidate/Formal 状态、Proposal、Formal MappingRevision 和 Commit 通过稳定关联表达。运行状态和执行结果不污染图对象，候选内容不会进入正式查询。
