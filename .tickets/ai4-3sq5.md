# 中央预审的通知收件人无人可解析：writer 读不到 published_by，定义里也没说发给谁

ADR-0004 定的口径是「PO 收件人取最近一次正式版本的 `published_by`」。领域侧也确实已经
把它投影出来了——`get_formal_mapping` 的返回里就有 `"published_by": "project-owner"`。
但这条事实到不了 `send_notification`：

- `centre-prereview-writer` 的 `allowed_tools` 只有 `append_prereview_log` 与
  `send_notification`，**没有 `get_formal_mapping`**，所以它拿不到 `published_by`；
- 定义里对收件人只有一句「发一条 `prereview_completed` 给项目负责人」，
  没有说这个人的 `principal_id` 是什么、从哪里取；
- 邮箱服务的 `recipients` 要求 `[{"principal_id": "..."}]`，缺这个字段直接判 `invalid`。

三件事叠起来，writer 只能猜。

## 一、实测（真机，不是推断）

真 key + 三个 MCP 全起，跑完整五步，候选也真的走完了读→判→写：

- `append_prereview_log` **成功落库**（`mapping_prereview_report` 一行，
  `rule_set_version=1.0.0`，`checks` 三条齐全）；
- 紧接着的 `send_notification` 两次都失败，`notification_delivery` 里留下两条
  `delivery_status=invalid` 的记录，`error_summary=invalid`；
- 模型两次猜的形状都不对：一次是 `[{"role": "project_owner"}]`，
  一次是 `[{"project_owner": "project_owner"}]`。

**注意这不是模型笨。** 它没有任何途径知道正确的 `principal_id`，而
`email-service` 的卡片和定义都没告诉它。换一个更强的模型只会换一种猜法。

我把 `person:owner` 手工喂给 `send_notification` 验证过形状：请求通过了内容校验，
走到收件人解析这一步，返回 `registry_unavailable`——那是 Registry 没起，不是形状问题。
也就是说**形状对了之后，这条链只差 Registry 里真有这条登记**。

## 二、为什么现在没人发现

`ai4-xkbd`（通知收件人与三种 kind）与 `ai4-ndu0`（经 Registry 解析收件人）都是在
**领域侧/服务侧**落的口径，验的是「拿到正确 principal_id 之后能不能发出去」。
中央 Agent 这一侧是另一条路径——它的定义文件里从来没有写过收件人从哪来。
两侧各自都绿，接缝是空的。

## Acceptance Criteria

- [ ] writer 能拿到本域项目负责人的 `principal_id`，来源是 ADR-0004 那条派生事实，不是新名册
- [ ] 定义文件里写明「收件人取 `get_formal_mapping` 返回的 `published_by`」，不再是「发给项目负责人」这种只对人有效的说法
- [ ] `published_by` 缺失时不猜：不发通知，在结果里记明确原因（例如 `recipient_unresolved:published_by_missing`），与 `task_owner_id` 缺失的处理一致
- [ ] 有测试断言模型收到的 `recipients` 含 `principal_id`，且该值等于本域 `published_by`
- [ ] 真机跑一轮：`notification_delivery.delivery_status` 不再是 `invalid`
