# 中央 Worker 的命令文本仍是 Execute TaskNode 标识符，模型拿不到本轮的域与事件事实

`gateway/subscriber` 里那一句 `command_text=f"Execute TaskNode {task_node_id} triggered by {trigger_ref}"`
是端侧 `ai4-1e9e` 修过的同一类缺陷换了个位置：把标识符当成任务交给模型。规格
`docs/superpowers/specs/2026-10-28-centre-agent-runtime-template-port-design.md` 的
「一轮 loop 的输入不是标识符拼出来的」已经明确否掉了这个形状，但代码没跟上。

## 一、实测（真机，不是推断）

用真 key（`deepseek-flash`）、三个领域 MCP 全起（8710 / 8720 / 8750）、卡片令牌补成
`Authorization` 头的条件下跑一轮 `FastAgentDeepSeekRuntime.run()`：

- 命令文本是 `Execute TaskNode node-e2e-1 triggered by ...` 时，intake 的回复是
  「我需要先确认域标识才能发起读取——本批候选没有给出 `mapping_domain_id` 和
  `wiki_domain_id`」，**一个工具都没调**，链路停在第一步。
- 同一套环境，只把命令文本换成「本轮事实：`mapping_domain_id=sciweave-mapping`、
  `wiki_domain_id=sciweave-wiki`、触发事件、去抖窗口」之后，五个 Agent 全部跑起来，
  领域侧的 `audit_call` 真的落到了 `list_reviewable_candidates` /
  `get_formal_wiki` 这些读工具上，`STATUS: completed`。

也就是说：**接缝是通的，缺的是「告诉模型这是哪一轮」这件具体的事。**
这不是模型能力问题，也不是令牌问题——同一份配置换个字符串就能跑。

## 二、为什么现在没人发现

`ai4-qula`（事件落成执行记录并派发）还没落地，所以生产路径上根本走不到这一步；
而单看 `worker_runner.py` 这一行，它长得跟端侧修之前的那行一模一样，容易被当成
「已经修过」的遗留物。两件事叠在一起，这条缺陷一直没被任何票覆盖（`grep` 全仓
`.tickets/` 无命中）。

## Acceptance Criteria

- [ ] 交给模型的文本由「定义里的预审指令 + 本轮事实」组成，不再是 `Execute TaskNode {id}`
- [ ] 本轮事实至少含：域标识（mapping 与 wiki 各一）、触发事件类型、去抖窗口；来源是执行记录，不是调用方临时拼的字符串
- [ ] 执行记录里存的是这些事实本身，不是一个待解析的字符串（否则等于把解析责任推给模型）
- [ ] 有测试从 `_execute()` 这一层断言模型收到的文本含域标识，不含裸 node id
- [ ] `ai4-qula` 落地后不需要再改 `worker_runner.py` 就能跑通一轮真机预审
