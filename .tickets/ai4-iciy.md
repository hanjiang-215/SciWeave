# 正式版本前进后候选重放与冲突审核规则

此前讨论的前提：TerminusDB candidate branch 是从某个正式版本派生的完整状态，不是单节点修改包；多个候选可以修改不同对象。一个候选正式化后，其他候选不能因此自动丢弃，也不能未经检查直接并入新正式状态。中央审核需要基于结构化变更摘要判断重放结果，并识别冲突或不确定情况。此票只收敛产品治理规则，不决定具体算法或 API。

## Design

## Question
当一个基于正式版本 B 的 Proposal 正式化并产生 B′ 后，其他基于 B 的候选应如何保留并推进？请决定：
- 候选是完整快照、相对基线的变更集，还是两者都需保留；
- 中央审核如何分类可安全重放、明确冲突和语义不确定的变更，以及结构化摘要应提供哪些审阅信息；
- 可安全重放的变更能否自动生成基于 B′ 的新候选；重放后是否必须重新经 Project Owner 审核；
- 哪些相互依赖的修改必须作为一个不可拆分的审核/正式化单位；
- 这些规则对 Research Mapping 与 Wiki、首版与后续能力分别适用到什么程度。

## Notes
保持原候选及其基线、审核和历史关联可追溯。不要预设“不同节点必然无冲突”，也不要把存储层 rebase 成功当作业务审批。

## Acceptance Criteria

给出候选相对基线和正式化后的生命周期规则；定义中央审核结论类别及结构化摘要的最低内容；明确自动重放与重新审核边界；明确不可拆分变更集规则；标明 Research Mapping/Wiki 和首版/后续阶段范围。

## Resolution — 候选重放、混合与正式化治理

### 候选数据和审阅池
- TerminusDB 保存每个候选的完整状态与提交历史；SQLite 保存治理元数据和审阅索引，包括 TerminusDB commit/hash、基准 Formal Revision、涉及对象/字段、结构化变更摘要、候选来源关系、中央分析结果、PO 处理结果及正式化 Revision 关联。SQLite 不重复保存候选正文。
- 每轮中央审核以同一个当前 Formal Revision 为基准，纳入所有尚未处理的候选提交，并对候选池整体进行语义分析，不限于两两比较。
- 对候选的兼容性以组合后的语义及约束为准，不以节点或字段标识是否相同作为唯一冲突依据。中央 Agent 可提出兼容组合、冲突解决或放弃方案；对语义依据不足的组合不应作为已验证兼容方案呈现，需交由 PO 通过 Codex/MCP 继续处理或明确放弃。

### 方案生成和审核
- Central Agent 可生成一个或多个完整候选方案，例如采用单个候选、组合可兼容的变更、部分混合或建议放弃；全部来源内容、基准、结构化摘要、Diff、影响范围、判断依据和方案取舍均向 PO 呈现。
- PO 通过自己的 Codex 经授权的专用 MCP 选择方案，也可要求 Codex 经 MCP 修改或组合方案。任何修改都生成新的不可变候选版本；Central Agent 重新校验，PO 批准的是该确切版本。Central Agent 不替代 PO 作最终选择或正式批准。
- 正式化必须针对一个完整的新候选方案；要同时采用多个来源的变更，先形成新的 blend 候选，不直接把多个旧分支当作一个正式版本。

### 来源提交处置与留存
- 本轮审核池中的每项来源提交，在所选方案正式化成功后必须记录明确处置：`selected`、`blended`、`partially blended` 或 `abandoned`。状态写入 SQLite，并通过消息队列通知提交者。
- “部分混合”是来源提交整体的治理状态；原 TerminusDB 提交保留，但后续不再复用该提交。混合结果由新候选提交承载，来源关系和实际采纳情况可追溯。若要继续处理未纳入的内容，应创建新的提交。
- 仅在正式化成功后确认上述最终处置状态；候选生成或选择尚未成功正式化时，不把来源提交记为已处理。

### 适用范围
- 同一治理语义适用于 Research Mapping 与 Wiki，但两者继续保持独立的 MCP、存储和领域校验；首版可限制实际并发处理能力，不将单候选写成永久产品限制。
- 本决策确定产品治理规则，不规定冲突检测算法、TerminusDB API 或具体 SQLite 表结构。
