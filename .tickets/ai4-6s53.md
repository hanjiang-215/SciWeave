# Mapping 候选提交与校验纵向实现

实现 Research Mapping 变更从正式基线进入可审阅候选的纵向路径：接收一个符合领域模型的 TaskNode/DependencyEdge 变更单元，执行结构和关系校验，在隔离候选中保存不可变快照，并记录对应治理对象与审计证据。

## Design

遵循已关闭的 TaskNode/DependencyEdge 字段模型 `ai4-t5zl`、`ai4-r3so`、Proposal 生命周期 `ai4-xrxw` 与 SQLite 持久化规格 `ai4-mjku`、候选分支验证 `ai4-2alw`；适用规格见 `docs/superpowers/specs/2026-10-19-research-mapping-content-persistence-model-design.md` 和 `docs/superpowers/specs/2026-10-19-research-mapping-candidate-governance-record-model-design.md`；正式基线读取复用本地图的 Mapping 正式版本查询任务。候选提交不改变当前正式指针，重复提交按已有幂等语义处理。Python + uv；SQLite 保存治理状态，TerminusDB 保存图快照，不假设未确认的 SDK/API。

## Implementation Contract

- **初始基准范围：** 当前候选提交仅支持已有正式基准。不存在正式版本时，服务以稳定原因码 `formal_base_required` 拒绝提交；首版领域初始化应由正式化/领域初始化流程单独建立，不把空基准解释成 TerminusDB `main` 或可变 head。若未来支持从零创建，必须先定义领域级初始化授权、精确空图快照与并发唯一性规则。 在 `sci-weave/research-mapping/src/research_mapping/candidate_submission.py` 实现 `MappingCandidateService.submit(change_set, idempotency_key)`；扩展本项目既有 SQLite schema/Store 和 `TerminusStore`，不重建子项目骨架、不新增第三方依赖。
- **版本文档身份：** TaskNode/DependencyEdge 的 TerminusDB `@id` 必须按不可变 `version_id` 唯一生成；同一逻辑对象的新版本使用新 `@id`，旧版本留在继承的基准快照中。`logical_id` 只关联逻辑对象，不作为 TerminusDB 文档主键。候选写入前规范化版本 `@id`，并拒绝冲突/不一致的显式 `@id`。
- **输入与输出：** 输入必须绑定 mapping domain、提交者、精确 `base_formal_revision_id`、稳定提交身份、TaskNode/DependencyEdge 变更单元和幂等键。成功结果返回原 Submission/Proposal/CandidateCommit 稳定 ID、候选 branch 与精确 commit hash；拒绝或结果未知不返回可审阅候选。
- **校验与存储：** 按已关闭的 TaskNode/DependencyEdge 规格校验端点/版本/状态、禁止自环和 blocking 子图环；验证基准仍匹配当前正式版本。扩展 `TerminusStore.create_candidate_snapshot(domain_id, base_commit_ref, canonical_snapshot, idempotency_key)`，返回确认/明确失败/结果未知及精确 commit ref；候选正文仅由 TerminusDB 保存。SQLite 以单一本地事务写入 Submission、Proposal、CandidateCommit 及关联 AuditEvent。
- **幂等和失败：** 规范化 change set 后使用 SHA-256；重复的相同操作返回第一次持久化结果。幂等身份与提交者、领域、提交 ID、精确基准和内容摘要绑定；相同身份对应不同内容返回 `idempotency_conflict`。确定性校验失败返回稳定错误码；TerminusDB 明确失败返回存储错误。结果未知时保留已有存储证据并返回 `result_unknown`；仅在精确 marker、作者、Commit 和完整候选文档读回均匹配时按原身份确认。无法证明候选分支归属（尤其只有基准 head）的情况不得重置或写入，保持未知并交由受控对账，不承诺盲目重试可自动恢复；重试不得创建第二个逻辑 Submission 或覆盖既有候选。
- **测试与配置：** 新增 `tests/test_candidate_submission.py`，用临时 SQLite 和 Fake TerminusStore 验证成功、关系/环校验、过期基准、幂等重试/冲突、TerminusDB 明确失败和结果未知；按 Mapping 地图的 `.env` 变量和 README 命令验证，不依赖固定端口。

## Acceptance Criteria

- [x] 合法变更单元以不可变快照进入隔离候选，并生成可追踪的 Submission、Proposal、CandidateCommit 和审计关联。
- [x] 缺失关系目标、版本/状态违规、自环、blocking 子图成环或过期正式基准被拒绝；正式版本和既有候选不受影响。
- [x] 相同幂等身份及内容返回第一次持久化结果；同一提交身份绑定不同基准/内容/提交者时显式冲突，不覆盖原候选。
- [x] 候选快照精确记录 TerminusDB store/branch/commit hash 和规范内容摘要；SQLite 仅持有治理事实和精确定位。
- [x] TerminusDB 确认、拒绝与未知结果均可区分；未知结果不谎报成功、不盲目重写。只在原操作身份、marker、作者、精确 Commit 和候选文档完全读回匹配时确认；无法证明分支归属时保留 `result_unknown`，等待受控对账，不把这种情况承诺为自动恢复。
- [x] TaskNode/DependencyEdge 每个 `version_id` 映射为独立 TerminusDB `@id`；同一 `logical_id` 的不同版本不共享 `@id`，旧正式版本文档不被候选写入覆盖。
- [x] `test_candidate_submission.py` 覆盖上述成功与拒绝/失败/未知分支；标准库测试和已锁定环境验证命令记录在交付证据中。

**2026-10-21 候选写入接口核验**

此前仓库与本地服务检查未找到足够证据，未实现候选写入。本轮进一步核对 TerminusDB `v12.0.8` 源码和在仓库固定容器上的隔离数据库实测，已确认以下调用链：`POST /api/branch/{store}/{database}/{remote}/branch/{new_branch}` 请求体 `origin` 指向源分支；随后 `POST /api/reset/{store}/{database}/{remote}/branch/{new_branch}` 请求体 `commit_descriptor` 可使用 `{store}/{database}/{remote}/commit/{hash}` 指向精确基准；再向候选分支的 `/api/document/{store}/{database}/{remote}/branch/{new_branch}` POST 文档。创建分支响应只有通用成功状态，不带 commit 身份。源码证据：`https://github.com/terminusdb/terminusdb/blob/v12.0.8/src/server/routes.pl` 的 Branch/Reset handlers 与 `https://github.com/terminusdb/terminusdb/blob/v12.0.8/src/core/api/api_reset.pl`；分支 API 使用说明：`https://terminusdb.com/docs/branch-howto`。

真实隔离库探测已成功：创建分支后 reset 到较早 commit，分支日志头与目标 commit 相同；再写入候选文档并按精确 commit 读回，文档匹配。探测数据库随后删除。该实验确认了 API 顺序和 `commit_descriptor` 格式，但尚未实现生产适配器，也未验证并发/超时期间分支创建、reset、文档写入各步骤的完整身份对账；这些步骤需要稳定的分支命名、提交标记和读回规则，不能把“分支存在”当成功。因此结果未知重试仍未满足。Mapping 单测仍为 27 项通过、3 项集成测试默认跳过；验收未勾选，票保持 `in_progress`。
