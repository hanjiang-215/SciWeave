# Agent 注册、Map 执行关系与消息订阅边界

## Question

在已确认 TaskNode.executor_refs 是正式任务执行关系、registry 只保存 Agent 登记事实的前提下，明确 Agent 注册、消息订阅和任务消费如何衔接：Agent 身份、持有者、实例、TaskNode 版本引用和 consumer group 如何表达；消息发布与订阅如何依据正式 Map.executor_refs；registry 登记缺失、Map 指向未登记 Agent、registry 声称节点但不在 executor_refs、Agent 离线或注销时分别如何处理。

本票只决定消息队列与 Map/registry 的交界，不重新定义 registry 字段实现、Research Mapping/LLM-Wiki 的领域权限，或邮件服务实现。

## Design

已确认的输入决策：

- 正式 Map 的 TaskNode.executor_refs 是任务执行关系的权威来源。
- registry 只记录 Agent 身份、持有主体、部署和登记节点等事实，不单独授予消息消费权限。
- registry 登记节点但不在 executor_refs 中的 Agent 不能消费该 TaskNode 的执行消息。
- executor_refs 指向未登记 Agent 时，不应静默发布无人消费的自动执行消息，应进入可观测待配置/异常状态。
- Agent 离线或注销只改变登记/运行状态，不自动修改正式 Map.executor_refs。

待收敛的消息语义包括注册/订阅申请、精确 TaskNode 版本路由、agent_id 与 agent_instance_id、principal_id、consumer group、订阅授权、不一致处理、离线和注销后的重连与补偿。

## Acceptance Criteria

- [x] 明确 agent_id、agent_instance_id、principal_id、TaskNode 版本引用和 consumer group 的关系
- [x] 明确正式 Map.executor_refs 如何决定 task_handoff_ready 的目标和可订阅范围
- [x] 明确 registry 登记不授予消息消费权限，且与正式 Map 不一致时有可观察处理
- [x] 明确 registry 缺失、executor_refs 指向未登记 Agent、Agent 离线/注销和重连/补偿语义
- [x] 明确多个合法 Agent/监听者的消费者组与消息投递关系
- [x] 形成可交给 subscriber 和消息发布服务实现的订阅、排队、消费边界
- [x] 将结论回写消息队列地图和相关注册/Work Agent 实现票

## Resolution

- `agent_id` 是研究员创建的 Fast Agent Workflow 的稳定逻辑身份；一个 Workflow 可以由单个 Agent 或多个内部 Agent 组成，但平台只注册一个 `agent_id`。
- `agent_instance_id` 表示某台设备或某次部署实例；Registry 可以记录多个实例，但 Map 不引用实例。
- `TaskNode.executor_refs` 直接引用稳定的 `agent_id`，是正式任务分配和消息路由的权威来源；一个 `agent_id` 可以被多个 TaskNode 引用。
- Registry 只保存主体、Workflow Agent 和运行实例的身份及基本登记信息，不保存 `task_node_id` 集合或“负责哪些节点”的第二份事实。需要反向查询时从正式 Map 的 `executor_refs` 派生。
- 消息发布服务在正式 Map 与 Registry 之间做运行时关联：未登记的 `agent_id` 不发布自动执行交接并产生可观察配置异常；Registry 登记本身不授予消费权限。
- Agent 离线或注销只改变 Registry/运行状态，不自动修改正式 Map；负责人替换执行者时，通过新的候选版本修改 `executor_refs` 并正式发布。
- 第一版的订阅范围、消费者组和多个实例消费方式继续按上述逻辑身份设计，具体 topic、分区和 offset 语义由本地图其他前沿继续收敛。
