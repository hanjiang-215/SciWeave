# 混合候选的生成与作者身份

定义中央 Agent 生成混合候选时的写入面与作者归属：新建分支、不改他人候选、作者记为全部来源作者且不附带操作权、不允许二次混合。

## Question

混合候选写到哪里、作者是谁、来源作者对它有什么权、能否被再次混合。

## Design

### 生成

中央 Agent 针对同一正式基准上的多个可送审候选，可以把可兼容的部分合成一个**新的候选分支**。合成结果是一个普通的候选，走与人工候选完全相同的预审判定与 PO 批准流程，没有特殊通道。

约束：

- 只能新建分支，不改写任何已有候选，不改写正式版本。
- 混合候选不能再被二次混合。若混合结果有问题，PO 驳回，来源作者各提新候选，再混合一次。禁止套娃是为了让每个候选的来源集合始终是「人提交的候选」，可以一层读完。
- 语义依据不足的组合不得作为已验证兼容方案呈现。判断不了就说判断不了，不猜。

### 作者身份

`submitted_by` 记为**全部来源作者**。同时：

- 来源作者对混合候选**没有任何操作权**：不能编辑、不能推进、不能撤回、不能批准。
- 混合候选生成后直接进 PO 待审队列，中间没有人能改它。
- 要改动只能走驳回—重提—再混合。

理由：混合内容的责任分散在几个人身上，给其中任何一人操作权，等于默认他可以代表其他人处置这段内容。记为联合作者只解决「可追溯」，不解决「谁有权」。

### 与人工候选的差别

唯一差别是作者字段是多值的，以及候选正文里必须列明**每个来源候选 ID 与他们各自被采用了哪部分**。治理上不加新状态：它不叫 `merged`，仍然是 `candidate`，Pre-review 与批准路径完全相同。

## Acceptance Criteria

- [ ] 混合候选只能新建分支，不改写已有候选与正式版本
- [ ] 作者字段为多值，记录全部来源作者，并在正文列明来源候选与被采用部分
- [ ] 来源作者对混合候选无编辑、推进、撤回、批准权
- [ ] 混合候选不可被二次混合，需要改动时走驳回与重新提交
- [ ] 混合候选不引入新的 Proposal 状态，走与人工候选相同的预审与批准路径
- [ ] 语义依据不足的组合不被标记为已验证兼容
- [ ] 有回归测试覆盖多来源合成、来源集合可追溯、二次混合被拒绝
