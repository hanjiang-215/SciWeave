# mapping 候选的 snapshot 摘要与读取口径不一致，预审永远读不到候选正文

`MappingCandidateReader.list_reviewable()` 在拿到快照后做一次摘要比对：

```python
digest = record.get("candidate_snapshot_digest")
if digest and snapshot.content_digest != digest:
    ... reason_code="candidate_snapshot_digest_mismatch"
```

左边 `snapshot.content_digest` 是**整条 candidate 分支在那个 commit 上的全部文档**
（`SnapshotRead.confirmed()` 用 `sha256_json(payload)`，`payload` 来自
`?as_list=true`，含从 base 继承来的正式节点与边）；右边 `candidate_snapshot_digest`
是**本次提交的那几个文档**（`candidate_submission.py` 里
`sha256_json(change_set["nodes"] + change_set["edges"])`）。

两边永远不相等——只要 base 有内容。于是每一个「基于非空正式版本提交」的候选都会被
判成 `unavailable`，正文为空数组。

## 一、实测（真机，不是推断）

TerminusDB 起在 6363，用看板播种脚本造一条 T1→T2→T3 的正式版本，再以它为 base 提交
一个候选：

| 量 | 值 |
| --- | --- |
| 分支快照文档数 | 6（3 个正式节点 + 2 条边 + 1 个新候选节点） |
| 读取侧 `content_digest` | `0d633549…a08e56` |
| 存库 `candidate_snapshot_digest` | `ee4869d6…cd9d810d` |
| 只取新候选节点算摘要 | `ee4869d6…cd9d810d`（与存库一致） |

也就是说：**存库的值是对的，读侧算错了口径。**

后果在预审报告里直接可见——`checks` 里 `impact_scope` 判 `failed`，
`reason_code=impact_undeterminable`，`evidence_summary` 写「documents 为空数组，
无正文可读」，`permission_scope` 也因取不到 `task_owner_id` 判失败。模型没有编造，
它如实说了读不到；但读者会以为是候选本身有问题。

## 二、为什么现在没人发现

`ai4-he04` 落地读取器时用的假 Terminus 每次只回一个文档（
`tests/test_management.py` 里 `_ReaderTerminus` 的 doc 元组），于是整条分支快照恰好
等于本次提交的文档，摘要自然相等。被测的只有「摘要一致时放行」和「摘要不一致时拒绝」
两个分支，没有一条夹具包含 base 继承来的文档——而那才是真实的形状。

## Acceptance Criteria

- [ ] 读取侧与写入侧的摘要口径一致；不一致的时刻必须能指出是哪一边的定义变了
- [ ] 以非空正式版本为 base 提交的候选，`list_reviewable_candidates` 返回 `snapshot_status=available` 且 `documents` 含该候选自己的文档
- [ ] 回归夹具用「base 有内容」的分支快照，不是只有一个文档的快照
- [ ] 真正的内容被篡改时仍判 `candidate_snapshot_digest_mismatch`，不因为放宽口径而失守
- [ ] 同一处判断在 wiki 侧有对应实现时一并核对（`llm_wiki/candidate_reader.py` 是同一形状）
