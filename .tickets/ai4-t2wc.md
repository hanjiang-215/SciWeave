# 注册表登记中央 Agent 与开放面第四档

在注册表加 `kind` 区分端侧与中央，并为中央 Agent 定义开放面：读两套管理 MCP 的候选与正式版本，写预审日志，新建混合候选分支，其余全禁。

## Question

中央 Agent 是否进注册表、登记什么字段、它在开放面里属于哪一档。

## Design

### 进注册表，加 kind

中央 Agent 要进注册表。它与端侧 Agent 同表，用 `kind` 区分：

| `kind` | 谁 | 所属主体 | 部署位置 |
| --- | --- | --- | --- |
| `endpoint` | 研究员自持的 task-agent | 必填，`principal_id` | 部署者自行描述 |
| `centre` | 中央 Agent | 留空 | 中央服务器，不需要描述 |

不新增规则集版本等字段：那是预审报告里的内容，不是注册事实。注册表仍然只回答「谁在跑什么」，不因为多了中央这一类就变成配置源或授权表。

### 开放面第四档

在「端侧 Agent 的注册记录与中央服务开放面」(ai4-ujvn) 的三档之上加第四档：

| 调用方 | 能做什么 | 不能做什么 |
| --- | --- | --- |
| 中央 Agent | 读两套管理 MCP 的候选与正式版本；`append_prereview_log`；`create_merged_candidate` | 写正式版本；改已有候选；写草稿箱的接纳状态；调用 Owner 命令类工具；发起执行；下发任务 |

要点：

- **读的范围比端侧宽**：端侧只看得到自己提交的草稿，中央 Agent 要看到全部候选才能判冲突。这是它存在的理由，不是越权。
- **两个写工具分开授权**：见「预审报告的追加日志契约」(ai4-oz3s)。凭据可以共用，工具面必须分开。
- **不写草稿箱**：草稿的一审是人，中央 Agent 的工作从候选存在开始。

### 仍然不是权限系统

登记表本身不参与鉴权这一条不变。中央 Agent 的能力由它的工具面决定，登记只留痕。中央 Agent 跑在中央自己的服务器上，平台对它是有强制力的，所以它的收口可以做得比端侧硬——但那是工具面的事，不是登记表的事。

## Acceptance Criteria

- [ ] 注册表增加 `kind` 字段，取值 `endpoint` 与 `centre`，中央类目所属主体留空
- [ ] 不为中央 Agent 增加规则集版本等运行时字段
- [ ] 开放面增加中央 Agent 一档，读写范围明确到工具粒度
- [ ] 明确中央 Agent 读全部候选，不受「只看自己提交」限制
- [ ] 明确中央 Agent 不写正式版本、不改已有候选、不写草稿箱接纳状态
- [ ] 明确两个写工具分开授权，凭据可共用但工具面不合并
- [ ] 登记仍然不参与鉴权
