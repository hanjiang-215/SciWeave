# Task Owner 通道（MCP）与上游交接队列物理隔离

> 标题修订（2026-10-19）：本票原题为“Task Owner A2A Gateway 与上游交接队列物理隔离”。Owner 通道已改为 MCP，见下方决策修订记录；历史注释保留原貌。

## Question
确定端侧 Task Agent 的两类触发在物理层面的隔离方式：Task Owner 的补充、返修、重试、暂停和取消是否通过 MCP 调用常驻 Task Agent Gateway；上游 TaskNode 的一次性交接是否继续通过消息队列和上游收集器处理。需要明确 Gateway、上游收集器与短生命周期 Worker 的职责，MCP 请求的持久化、授权、审计、幂等性、取消语义，以及 Gateway 是否可在内部投递作业而不改变 Owner 通信语义。该票不选择具体消息队列、MCP SDK 或部署方案。

## Acceptance Criteria

形成可供后续流程设计使用的物理隔离规格：明确 Owner MCP 调用、上游队列交接、常驻 Gateway、常驻上游收集器和短生命周期 Worker 的边界；明确 Owner Command 的持久化与审计，以及 Worker 释放后继续接收 Owner 指令的方式。


## Notes

**2026-10-19T03:03:47Z**

设计与验证更新（2026-10-19）：确认 A2A 不要求执行 Worker 常驻。物理隔离采用：Task Owner 的 Codex -> A2A -> 常驻 Task Agent Gateway -> 按需创建/控制短生命周期 Worker；上游 TaskNode 审核通过 -> 上游交接消息队列 -> 常驻上游收集器 -> 收齐并满足 Dependency Edge 后创建 Worker。Gateway 和上游收集器常驻，Worker 在一个 loop 后释放；Buffer、Owner Command、Execution Record 和 AuditEvent 留在平台侧。A2A 原型验证已在 drafts/fast-agent-startup-test/ 通过，验证的是本地 A2A server 与 fast-agent A2A client 的最小启动与响应，未验证 Gateway 的授权、命令持久化、幂等、取消或内部作业投递。

**2026-10-19T05:47:44Z**

Wayfinder 前沿结论（2026-10-19）：Q1-Q8 已确认的 A2A/Gateway 物理边界：Owner 的 Codex -> A2A -> 常驻 Task Agent Gateway；Gateway 负责鉴权、Owner Command 持久化、幂等、审计、任务状态和按需创建/控制短生命周期 Worker。上游 TaskNode 审核通过 -> 消息队列 -> 常驻上游收集器；收齐必要交接且满足 Dependency Edge 后创建 Worker。A2A 不替代上游内部队列。

**2026-10-19T06:14:49Z**

Wayfinder 讨论修正（2026-10-19）：基础设施恢复后，平台只恢复消息监听服务对持久化日志中未确认消息的读取；已确认消费的消息不重复创建执行。此前失败的执行由使用者通过 Web 看板或 Codex/MCP 判断，并决定是否提交新的执行尝试。平台不因服务恢复自动重做失败任务。

**2026-10-19T20:10:00Z**

决策修订（2026-10-19）：Owner 通道由 A2A 改为 MCP。事实依据：Codex CLI、Cursor、Claude Code 对外扩展面只有 MCP，均未内置 A2A 客户端；A2A 的 SDK 只提供自行编写客户端的能力。A2A 面向“Agent 之间协作”，而 harness 是 Agent 宿主，协议定位不匹配，因此不能假设 Task Owner 的 Codex 能直接作为 A2A 客户端。

修订后的边界：

- Task Owner 的 Codex → **MCP（Streamable HTTP）** → 常驻 Task Agent Gateway。Gateway 是 MCP server，暴露 `submit_owner_command`、`query_execution`、`cancel_execution`、`list_pending` 等工具；Codex 侧只在 `mcp_servers` 中注册地址与令牌，不承载业务逻辑。
- 上游 TaskNode 审核通过 → 消息队列 → 常驻上游收集器 → 创建 Worker。该路径与本次修订无关，保持不变。
- 不使用 stdio 传输：stdio 会让 Codex 自行 spawn 进程，破坏 Gateway 常驻、SQLite 单写者和跨会话串行调度这三个前提。
- A2A 不再用于 Owner 通道。若后续需要“Agent 与 Agent 直接协作”，另立阶段讨论，不影响本票边界。

Human Input 语义随之改写：fast-agent 的 `INPUT_REQUIRED` 不再通过 A2A `TASK_STATE_INPUT_REQUIRED` 表达，而是由 `query_execution` 返回 `waiting` 状态与问题文本，Owner 通过新的 `submit_owner_command` 以同一 `execution_id` 续接。

## Resolution

本票要的物理隔离结论已定，关闭。

Owner 通道采用 MCP Streamable HTTP：Task Owner 在自己的 harness 里注册端侧 Gateway 地址与本地令牌，Gateway 暴露 `submit_owner_command`、`query_execution`、`cancel_execution`、`list_pending`、`review_execution`、`health`。Human Input 由 `query_execution` 返回 `waiting` 与问题文本表达，Owner 以同一 `execution_id` 提交新的 Owner 命令续接。

上游 TaskNode 的交接走消息队列，与 Owner 通道物理隔离。

端侧自持修订（2026-10-21，依据「Task Agent 改由研究员端侧自持」ai4-we38）：上述两条隔离结论不变，但两端位置改变。Owner 通道与上游订阅都落在研究员自己的电脑上，端侧订阅器主动连接中央队列，Owner 通过本机回环调用 Gateway。A2A 不用于 Owner 通道，原型仅作 fast-agent-mcp 协议能力证据。

详细状态机与协议见「最小 Task Agent 项目组实现规格」及其修订。
