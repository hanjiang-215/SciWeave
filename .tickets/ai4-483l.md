# T1 校验脚本把行尾差异判成快照篡改，失败注入给错理由

`humans/competition/demo-evidence/check_iris_input.py` 现在对仓库内的固定快照必定失败，演示第 2 段（T1 检查通过）无法演出。

实测（2026-10-27，本机 `feature/frank-qi`）：

```text
$ python3 check_iris_input.py iris_data.csv
{ "status": "failed", "reason_code": "source_hash_mismatch",
  "observed_sha256": "ea110d42c2240c77fd292751dfdc4db00c699fee569528ed33ca270838b6f9f4",
  "expected_sha256": "daaeb5e3e889d07fbdd44544f5a39fe2372a07172e25899d577be0ad74df9e65" }
```

根因是行尾，不是内容：

| 形态 | SHA-256 | 字节数 |
| --- | --- | --- |
| 仓库内快照（LF） | `ea110d42…b6f9f4` | 4464 |
| 脚本第 18 行写死的期望值（CRLF） | `daaeb5e3…df9e65` | 4615 |

`daaeb5e3` 是在 CRLF 工作副本上算出来的（同批 `iris_input_check.json` 是 UTF-16LE + CRLF，`check_script` 字段还带 Windows 反斜杠 `humans\\competition\\demo-evidence\\check_iris_input.py`）；提交进仓库的 blob 已被规整为 LF（`git cat-file -p HEAD:...iris_data.csv | sha256sum` = `ea110d42…`），于是哈希与文件在仓库内自相矛盾。

连带后果：`iris_data_failure_inject.csv` 本该命中 `missing_columns`（该文件表头就是少了 `class` 列），但第 38 行的哈希检查排在第 43–46 行的列检查之前，失败注入现在同样返回 `source_hash_mismatch`。演示第 4 段的口播正是「缺列被 T1 拦截」，实际会看到同一份逻辑对两份不同文件报同一个理由，恰是评委最容易追问的点。已存档的 `iris_input_failure.json` 记录的就是这个错误理由（`cf9188f1…` 是失败注入文件的 CRLF 哈希）。

## Design

两处改动，都在 `check_iris_input.py`：

1. **哈希按内容归一化。** `sha256_of` 读取全部字节后把 `\r\n` 替换为 `\n` 再计算。这样 LF 检出、CRLF 检出、官方下载的 CSV 得到同一个哈希，快照校验只对内容敏感，不对检出工具的换行策略敏感。文件只有 4.6 KB，整块读取即可，不需要保留分块迭代（分块还会在 `\r`/`\n` 恰好跨块时漏替换）。
2. **列检查前移到哈希检查之前。** 列结构是结构性判定，来源哈希是溯源判定；先判结构可以让「缺列」这种可解释失败拿到自己的 `reason_code`，而保留全部列但改过数值的文件仍会被哈希拦下，溯源判定没有被削弱。

`EXPECTED_SHA256` 同步改为归一化后的值 `ea110d42c2240c77fd292751dfdc4db00c699fee569528ed33ca270838b6f9f4`。

同一份脚本在 `humans/competition/sciencpal-onboarding/checks/` 下有一份逐字节相同的副本（sha256 `6674f2df…`）。本票只要求 `demo-evidence/` 那份正确；若 `ai4-3vkc` 先完成去重，则只需改一份。副本未去重前必须两份同改，否则沙箱里跑的是旧逻辑。

验证命令与结果：

```text
$ cd humans/competition/demo-evidence
$ python3 -m unittest discover -s tests -q
Ran 20 tests ... OK

$ python3 check_iris_input.py iris_data.csv
{"status": "ok", ..., "snapshot_sha256": "ea110d42...b6f9f4", "row_count": 150}   exit 0

$ python3 check_iris_input.py iris_data_failure_inject.csv
{"status": "failed", "reason_code": "missing_columns", ...}                        exit 1
```

**设计比本票原方案多走了一步，理由记录在此。** 票里写的是「列检查前移到哈希之前」，实现时发现只前移列检查是不够的：`check()` 共有四个结构判定（列、行数、缺失值、类别计数），哈希夹在列检查之后、行数检查之前，会导致凡是走到行数检查的文件必然已经通过哈希——也就是必然就是锁定快照，于是 `row_count_mismatch`、`missing_values`、`class_count_mismatch` 三个理由码永远不可达。最终改为**哈希放到最后**：结构判定先跑并各自给出理由码，哈希作为成功前的最后一道门。这同时满足「缺列报 `missing_columns`」和「数值被改仍被拦下」，且不牺牲任何诊断。

评审时对这条做了一次反向验证：把哈希检查挪回最前面，测试立刻红了 5 条并报 1 个 error（三个行数/缺失值/类别计数用例 + 列缺失用例 + 不可解码用例）。

**行为增强（评审提出，超出原票范围）**：`check()` 原先对不可解码文件、不存在的文件直接抛异常。现在两者都返回 `reason_code: unreadable_input` 的结构化记录，退出码 1。演示现场误传 UTF-16 副本时看到的是 JSON 而不是 traceback。

**测试**：`tests/test_check_iris_input.py` 共 11 条，覆盖 LF 通过、CRLF 通过、缺列、改值（溯源未被削弱）、行数、缺失值、类别计数、不可解码、文件缺失、CLI 退出码 0/1，外加一条跨五处引用的一致性断言。其中「改值」这条做过变异验证：把 `EXPECTED_SHA256` 临时改成篡改文件的哈希后 `check()` 返回 `ok`，说明该用例失败时只可能来自哈希，不是被结构层顺带挡住的假阳性。
