# email-service 的发送端口与收件人解析仍是 Unbound 占位


## Notes

**2026-10-26T19:35:34Z**

审查发现（2026-10-27）：`email-service` 的入口装配的是两个 Unbound 占位实现，人工通知这条腿在真实部署里发不出去。

证据：`src/main.py:16` 传入 `UnboundMailSender()`；`src/ports.py:76` 的 `UnboundRecipientResolver.resolve` 直接抛 `recipient_resolver_unavailable`，`ports.py:83` 的 `UnboundMailSender.send` 直接抛 `sender_unavailable`。而 `README.md:3` 写的是「服务通过 Registry 的 Streamable HTTP 解析收件人」，代码与文档不一致。

影响：协调服务发出的 `human_notification_intent` 会在 email-service 侧稳定失败。协调服务不会把它记成已发送（这点是对的，`_NoopNotificationPublisher` 与投递失败都会保留等待事实），但研究员/负责人实际上收不到任何通知，只能靠查 dashboard。

建议实现（按推荐方案）：
1. `RegistryContactResolver`：经 Registry MCP 查询 principal 的联系方式，把 `contact_missing`/`contact_disabled`/`principal_not_found` 映射成现有稳定错误码；用进程内 MCP stub 覆盖三类错误与成功路径。
2. `SmtpMailSender`：用标准库 `smtplib`，主机/端口/凭据/发件人全部来自环境变量（`SCIWEAVE_EMAIL_SMTP_*`），未配置时**不**回退到占位，而是启动即报缺哪个变量；`send` 的超时与失败映射到现有可查询终态。
3. 保留 Unbound* 仅作为测试替身，不在入口装配。

验收：新增两类适配器的单测（不联网，smtplib 与 Registry 都用替身）；入口在缺少 SMTP 配置时启动即失败并说明缺什么；`docs/验证命令.md` 与 email-service README 的口径同步。
