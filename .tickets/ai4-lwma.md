# 端侧 Worker 没有发布 `task_completed` 的通道：完成事实到不了协调器

`ai4-te1v:96` 裁决：`task_completed` 由 Task Agent Worker 在「草稿写入草稿箱成功、且 ExecutionRecord 保存 `completed` 与 `draft_id`」之后**立即发布**，不等任何审核结论。协调器只消费它来解除下游依赖条件。

套件里没有任何代码发这条消息。`runtime/src/work_agent_runtime/` 与 `service-template/worker/` 中 `grep -rn producer` 只命中注释；`run_workflow()` 完成时写 `ExecutionRecord` 与草稿，然后返回，不发消息。全仓库的 `task_completed` 只出现在三处：`payloads.py` 的 schema、协调器的 `_handle_task_completed`、以及 `service.on_task_completed`——**没有一个生产者**。

后果：协调器的「上游完成 → 解除下游」路径在生产上不可达。下游要等下一次无关的 `formal_revision_published` 才会被重算，也就是「谁随手改了一笔，谁的下游才动」。

这**不是信封格式问题**（那归 `ai4-derq`）：即使格式完全对齐，端侧也没有出站通道。缺的是四样东西：

1. broker 地址与出站凭据——跑在研究员笔记本上的 Worker 要连中央 Redpanda；
2. topic 写授权——现有凭据是订阅端的消费者组，语义完全不同（订阅是拉、发布是推，授权面也不同）；
3. 失败重试——Worker 结束时进程即将退出，消息没发出去就没有下一次机会；
4. at-least-once 语义——重试会重复发，协调器一侧的去重键要能挡住。

「本地已完成」与「消息已发出」之间必须选一个次序，这个选择是本票的核心问题。

## Acceptance Criteria

- [ ] 明确端侧 Worker 发布 `task_completed` 的触发点，并说明它与「写 ExecutionRecord」「退出进程」的先后。载荷字段 `execution_id` / `draft_id` / `completed_at` / `result_ref` 全部可从 `ExecutionRecord` 取得，指出确切位置。
- [ ] 给出出站凭据与 topic 授权的方案，说明为何不能复用订阅端的消费者组凭据。
- [ ] 发布失败时的处置与重试语义明确：已完成的本地 ExecutionRecord 不得因发送失败而回退；至少一次投递的重复由协调器侧去重键挡住。
- [ ] 至少一条端到端测试证明消息真的被协调器的消费路径读到并解除下游——不是「发出去就算」。
- [ ] 与 `ai4-derq` 的裁决一致：`schema_version` 必填 int、字段名 `completed_version_ref`、信封为分层形状。
