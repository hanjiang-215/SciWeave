# Research Mapping 与 LLM-Wiki 访问边界必须独立

Research Mapping 与 LLM-Wiki 虽可共享部分治理原则，但实现时必须保持独立的领域管理 MCP、存储、校验器、候选/正式化流程、审计边界和调用方权限。研究员、Task Agent、Centre Agent 与 Project Owner 在两个领域的可读、候选提交、候选审阅和正式化能力必须分别定义，不能用一套跨域权限判断或共享接口隐式放权。

请在 Research Mapping 与 LLM-Wiki 的实现中分别确认：
- 正式内容、候选内容和草稿的读取边界；
- Task Agent、研究员、Centre Agent、Project Owner 的工具能力；
- 领域内负责人和正式发布人的授权来源；
- 跨域引用只通过稳定 ID/version ID 弱引用，不建立跨域写入或跨域原子权限；
- 注册表只提供事实留痕和通知目标发现，不成为两个领域的统一授权源。

这张票作为实现前的跨域约束，供 Research Mapping 与 LLM-Wiki 负责人分别落实，不要求合并两个领域的 MCP 或存储。

## Design

当前已确认的领域边界：Research Mapping 与 LLM-Wiki 分别拥有独立 MCP、存储、校验、候选分支、Formal Revision/WikiRevision 和审计链；共同治理原则不等于共享权限实现。

需要避免的错误：
1. 用同一套 read/write 权限判断同时暴露 Map 和 Wiki；
2. 让调用方通过一个跨域工具绕过任一领域的候选或正式化门禁；
3. 把 TaskNode Owner、Wiki Curator/Resource Owner、Project Owner 或 Centre Agent 的角色直接互相映射；
4. 让 registry 的登记事实成为领域授权依据。

Map 的 TaskNode/DependencyEdge 责任和正式版本属于 Research Mapping；WikiDocument/WikiRevision/ResourceVersion 的责任和正式版本属于 LLM-Wiki。跨域只保留显式稳定引用。

## Acceptance Criteria

- [ ] Research Mapping 与 LLM-Wiki 分别列出正式读取、候选读取/提交、候选审阅和正式化的调用方能力边界
- [ ] 两个领域分别执行未授权调用拒绝，不能依赖隐藏工具或提示词约束
- [ ] 两个领域分别使用自己的 MCP、存储、校验和审计边界
- [ ] 跨域引用只使用稳定 ID/version ID，不支持单次跨域 Proposal、跨域写入或跨域原子正式化
- [ ] registry 的事实登记不参与任一领域的鉴权决定
- [ ] 实现说明分别记录 TaskNode/DependencyEdge 与 WikiDocument/WikiRevision/ResourceVersion 的责任、执行和发布权限
- [ ] 在相关实现票或 README 中回写本约束和验证证据
