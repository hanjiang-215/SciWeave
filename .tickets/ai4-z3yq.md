# 套件的配置层没有任何生产调用方：三套 libs 改了也不生效

套件把 `libs/agent-libs/`、`libs/mcp-libs/`、`libs/workflow-libs/` 当成研究员可改的配置面写进了 README、`.env.example` 和 `deploy-task-agent-skills/create-agent/`。实际上**这三个目录在任何生产路径上都没有被读取过**——加载器写好了、测好了，但没有人调用。

## 一、证据

`runtime/src/work_agent_runtime/` 里五个加载器/转换器，在 `runtime/src` 与 `service-template` 全树（排除 `tests/`）的调用方：

```
load_config                 → 0 处（只有 config.py 内部互相调用）
load_agent_registry         → 0 处
load_mcp_registry           → 0 处
load_workflow_libs          → 0 处
load_workflow_yaml          → 0 处
workflow_to_fast_agent_input→ 0 处
```

`.env.example` 里却完整提供了六个路径变量（`AGENT_LIBS_PATH` / `MCP_LIBS_PATH` / `WORKFLOW_LIBS_PATH` / 三个 `LOCAL_*`），`install.sh` 也照拷 `libs/`。研究员照着 `create-agent` 技能改完 YAML、改完 `.env`，**跑起来不会有任何变化**。

## 二、跑起来的到底是什么

`fast_agent_runtime.py:127-137` 里 agent 是完全硬编码的：

```python
agent_name = f"worker-{request.task_node_id}"
@fast.agent(
    name=agent_name,
    instruction=(
        "You are a SciWeave researcher-side Task Agent. Complete the "
        "owner's command concisely and state what you did not verify. "
        f"Connection scope: {self.settings.connection_scope}. "
        f"Session: {request.session_id}."
    ),
    model=f"openai.{self.settings.model}",
    use_history=True,
)
```

instruction 是常量，agent 名是模板，`_write_fast_agent_config()` 生成的 `fast-agent.yaml` 只有两行（`compaction.auto` / `session_history`），**一个 `mcp.servers` 都没有**。所以研究员侧的 agent 拿不到任何 MCP 工具。

这是 `ai4-x0ay` 第 6 节要解决的问题的一半。那一节写的是「`allowed_mcp_resources` 转成 `mcp.servers`」，前提是配置真的会被加载——但加载这一步现在根本不存在。x0ay 按现状实现会得到一段没人调用的转换代码，和现在这五个加载器一样。

## 三、`agent-definitions/` 也是悬空的

README 第 7 行称它是「兼容入口的 Agent 定义」，`install.sh` 会拷贝它，但它同样不在任何生产读取路径上。真正被读的只有运行时环境变量 `SCIWEAVE_AGENT_ID` 与订阅的 topic 列表。

**`command_text` 的来源也没人给。** `worker_shell.py:42`：

```python
command_text=row["agent_definition"] or row["target_id"],
```

也就是说模型收到的「指令」要么是空字符串，要么是裸的 `task node id`（实测：`'node-2'`）。真实交接消息里承载任务内容的是 `payload`（`target_node_version_ref`、`upstream_source_refs` 等），而 payload 在 `handle_inbound` 里被整个丢掉了——它只传 `target_id` 和 `event_id`。

## 四、范围

本票只做「让配置面真的接上」这一件事：

1. `service-template/worker/src/main.py`（或 subscriber 拉起 worker 的那一侧）启动时必须加载 `AGENT_LIBS_PATH` / `MCP_LIBS_PATH` / `WORKFLOW_LIBS_PATH`，加载失败则**启动失败**，不静默退化；
2. `fast_agent_runtime.py` 的 instruction 与 agent 名从加载到的 `AgentDefinition` 取，不再硬编码；
3. `agent-definitions/` 与 `libs/agent-libs/` 的关系写清楚：谁是权威，另一个是否还需要存在；
4. `command_text` 的来源要有个说法（哪怕结论是「本票不解决，归另一张票」，也要写下来并链接）。

**不在本票范围**：

- `mcp.servers` 注入与三种 transport 形态 → `ai4-x0ay` 第 6 节；
- worker 的启动形态（子进程 vs 内联）→ `ai4-0fwc`；
- 信封取值 → `ai4-u9gj`；
- 加载器本身的校验逻辑（`unknown_field` 等）→ `ai4-4r0h` 已交付，不动。

**2026-10-27 补充：不是「忘了传」，是签名层就没有入口**

复核运行时装配链的签名，`AgentDefinition` / `TaskAgentConfig` 在这条链上**根本没有可传入的位置**：

```
build_agent_runtime params:                ['environ']
FastAgentDeepSeekRuntime.__init__ params:  ['self', 'settings']
FastAgentSettings fields:                  ['api_key', 'base_url', 'model', 'home', 'session_dir', 'connection_scope']
```

`environ` 只用来读六个标量（Key、base URL、模型名、两个目录、连接域）。所以这不只是「worker 的 `main.py` 少写了两行加载」——即使补上加载，也没有参数能把结果交给运行时。要给 `FastAgentDeepSeekRuntime.__init__` 加一个 config 入口，并让 `_write_fast_agent_config()` / `@fast.agent(instruction=...)` 从它取值。

这条也解释了为什么 `ai4-x0ay` 第 6 节（`mcp.servers` 翻译）不能只改 `config.py` 里的转换函数：转换出来的 dict 同样无处可去。

## 完成（2026-10-27，Frank Qi）

新增 `runtime/src/work_agent_runtime/assembly.py`，`load_worker_config(environ)` 是唯一读环境变量并返回 `WorkerConfig` 的入口；`build_agent_runtime()` 在构造运行时时调用它。链路变成 `环境 -> WorkerConfig -> fast-agent`，中间没有「转换好了但没人用」的悬空段——这正是本票反对的形态。

### 四套目录的定位（AC 第 4 条）

| 目录 | 内容 | 结论 |
| --- | --- | --- |
| `agent-definitions/agents/` | `AgentDefinition`：identity / instruction / model / 允许的 MCP | **权威**。这是「agent 是谁」 |
| `libs/agent-libs/` | `AgentResource`：prompt / formatter / task_mode / validator / workflow_helper | **保留**。这是 agent 按 `名字@版本` **引用**的材料 |
| `libs/mcp-libs/` | MCP 工具卡 | 保留，`MCPRegistry` |
| `libs/workflow-libs/` | 工作流声明 | 保留，唯一出处（`ai4-4zjz` 已确立） |

两个目录都留下，因为它们是两种东西，不是同一个东西的两份。README 第 7–8 行原先把 `agent-definitions/` 写成「兼容入口」，暗示它可以被合并掉——实际它是唯一放 Agent 定义的地方，`libs/agent-libs/` 里没有一个文件是 agent。这条已改。

`SCIWEAVE_AGENT_ID` 负责**选哪个 agent**，和它已经负责的「订阅哪个 topic」是同一个标识符。之前这个变量只影响 topic，agent 名是 `worker-{task_node_id}` 模板生成的，所以每次执行都是一个新 agent，历史和（将来的）`mcp.servers` 都没法钉在某个定义上。

### instruction 与 model（AC 第 2、3 条）

`_instruction()` 现在取 `definition.instruction`，只在末尾追加两行运行期事实（connection scope、session id）——那两项不是定义的属性。没有 config 时（只有裸构造的单测会这样）才退回原来的常量。

`_model()` 是本票的额外发现：出厂定义全写 `configure-in-your-own-environment`，四个 workflow 示例全写 `configure-locally`，两个都是占位符。现在的规则是「以 `configure-` 开头的视为占位符，回退到 `DEEPSEEK_MODEL`；否则 YAML 里的真名优先」。不这么写，要么研究员永远无法按 agent 指定模型，要么出厂配置直接把 `openai.configure-in-your-own-environment` 发给 API。

### 测试

测试辅助挪到 `tests/fast_agent_doubles.py`：`python -m unittest tests.test_x` 与 `discover -s tests` 对「tests 是不是包」的判断不一致，跨测试文件 import 会在其中一种下失败。
