# 受理端禁止主题里的换行与回车

## 问题

`service.py:53` 的 `_KEPT_CONTROLS = frozenset("\n\r\t")` 是为了放行多行正文，但同一个白名单也放行了主题。`_has_disallowed_control` 对主题和正文用同一个判断，于是主题里可以有 `\r\n`。

实测（2026-10-26，直接喂 `_content_problem`）：

```python
subject = "hi\r\nBcc: evil@x.test"
_content_problem(caller, intent, {}) == False   # 判定为合法
```

也就是说这条通知会通过 `send_notification`，写进投递库，然后才在发送端出问题。

## 为什么现在没被打穿

纯属运气。`EmailMessage["Subject"] = "..."` 自己会抛：

```
ValueError: Header values may not contain linefeed or carriage return characters
```

所以只要发送端用标准库的邮件对象，注入就走不通——但它会在**发送阶段**失败，而不是在受理阶段被拒，调用方拿到的是一个 `permanent_failure`，无法区分「内容非法」和「发信服务挂了」。

将来谁图省事写 `f"Subject: {subject}\r\n"` 手工拼报文，这条就是可直接利用的 SMTP 头注入：主题塞进 `\r\nBcc: attacker@evil.test`，投递服务会自动把信抄给攻击者。

## 修法

`_content_problem` 里对主题单独判：

1. 主题禁止 `\r` 与 `\n`（`\t` 保留）；
2. 正文不变，仍允许 `\r` `\n` `\t`；
3. 违反时按现有 `invalid` 语义处理，走 `record_invalid`，记 `non_retryable_content`。

同时发送端必须用 `EmailMessage` / `headerregistry` 构造报文（`ai4-ceqq` 的第 ⑤ 条），两者都要做：一个是把非法输入提前拒掉，一个是不依赖「后来每个改发送端的人都记得」。

## 规格影响

`ai4-f985` 的 Testing Decisions 写的是「主题或正文里的控制字符（换行、回车、制表符除外）」，把主题和正文混成一条了。本票是该句的修订，实现完成后在 `ai4-f985` 追加带日期的修订注记，不重开该票。

## Acceptance Criteria

- [ ] `_content_problem` 对含 `\r` 或 `\n` 的主题返回问题（`True`），并对含 `\r` `\n` `\t` 的正文仍返回无问题（`False`）。
- [ ] 含 `\r\n` 的主题经 MCP `send_notification` 提交时状态为 `invalid`，不写入投递库，不调用发送端口。
- [ ] 含 `\t` 的主题仍被受理（`\t` 不是 header 分隔符，不构成注入）。
- [ ] 有测试直接覆盖上述三种输入，断言最终 `delivery_status`。
- [ ] 全量 pytest 通过；`python -m compileall -q src tests` 通过；`git diff --check` 通过。

## Not in Scope

- 不改正文的多行支持。
- 不改其他控制字符的判定（`unicodedata.category == "Cc"` 的既有逻辑不动）。
- 不做正文的敏感信息扫描——`ai4-f985` 已明确「不把凭据写进去是撰写方的责任」。
