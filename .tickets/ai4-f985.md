# email-service 通知意图协议与投递状态规格

## Problem Statement

SciWeave 的 Task Agent、Centre Workflow、交接协调服务和 Project Owner 管理流程都需要向负责人发送邮件提醒。目前尚未定义统一的通知调用契约，导致调用方可能直接持有 SMTP 凭据、重复发送同一通知、把邮件发送成功误解为业务状态变更，或在邮件服务失败时缺少可恢复的投递事实。

## Solution

建立独立的 `email-service` Python 子项目，首版只提供一个受鉴权的 MCP 写入工具 `send_notification`。调用方提交结构化 `human_notification_intent`，邮件服务解析收件人、校验主题和正文、使用统一公共邮箱发件，并持久化通知投递状态。

首版不消费 Redpanda 的通知 topic；MCP 是唯一输入入口。`human_notification_intent` 是 MCP 请求和邮件服务持久化记录的业务对象，不代表首版必须存在同名物理 topic。未来可增加队列适配器，但不能与首版 MCP 入口形成两套未定义的投递事实。

邮件服务只负责通知投递，不判断通知对应的业务事实，不修改 Research Mapping、LLM-Wiki、候选、正式版本、PendingHandoff 或 Task Agent ExecutionRecord，也不把邮件发送成功解释为任务完成或路线推进。

## User Stories

1. 作为 Task Agent Gateway，我希望通过 MCP 提交执行完成通知，以便 TaskNode Owner 及时审阅草稿。
2. 作为 Task Agent Gateway，我希望提交执行失败、返修完成和人工问题通知，以便负责人知道下一步需要通过 Gateway MCP 处理什么。
3. 作为 Centre Workflow，我希望通知 Project Owner 预审完成，以便 PO 通过自己的管理 MCP 作出正式化、返修或拒绝决定。
4. 作为交接协调服务，我希望通知目标负责人 Agent 未登记、Agent 不可用、目标未正式化或依赖未满足，以便人工处理阻塞。
5. 作为交接协调服务，我希望在正式路线确认没有后继 TaskNode 时通知 Project Owner，以便 PO 决定结束路线或创建新的候选任务。
6. 作为 Project Owner，我希望通过统一公共邮箱收到可识别的主题和正文，以便快速理解需要采取的动作。
7. 作为服务调用方，我希望只持有 email-service MCP 的服务凭据，而不持有公共邮箱的 SMTP 凭据，以便降低凭据扩散风险。
8. 作为通知服务，我希望通过 `principal_id` 解析收件人地址，以便人员更换邮箱时无需修改业务调用方。
9. 作为通知服务，我希望允许调用方传入主题和正文，以便保留不同业务场景所需的具体上下文。
10. 作为通知服务，我希望强制调用方提供 `notification_kind`，以便区分草稿、失败、预审、返修、Agent 不可用和路线终点等场景。
11. 作为通知服务，我希望使用 `notification_id` 和 `dedupe_key` 幂等处理，以便重复调用不会重复发信。
12. 作为调用方，我希望相同去重键但不同正文被拒绝，以便避免悄悄覆盖既有通知事实。
13. 作为通知服务，我希望区分暂时发送失败和永久发送失败，以便只对可能恢复的错误重试。
14. 作为通知服务，我希望进程重启后恢复 `pending`、`sending` 和 `retryable` 记录，以便不丢失通知。
15. 作为通知服务，我希望在收件人无地址、schema 不支持或内容非法时记录 `invalid`，以便错误可查询且不无限重试。
16. 作为通知服务，我希望记录调用者身份、通知类型、关联对象和发送结果，以便审计和排障。
17. 作为安全管理员，我希望调用方不能自定义 From 地址、SMTP 参数或凭据，以便统一公共邮箱发件。
18. 作为安全管理员，我希望邮件正文不包含令牌、密码、异常堆栈和完整候选正文，以便减少敏感信息泄露。
19. 作为运维人员，我希望查询单条通知的状态和错误摘要，以便处理发送失败。
20. 作为运维人员，我希望永久失败进入可观察的死信或失败记录，以便不会被无限重试。
21. 作为业务服务，我希望邮件投递失败不回滚正式 Map 或候选决定，以便通知故障不会破坏领域事实。
22. 作为业务服务，我希望邮件投递不发布 `task_handoff_ready`，以便通知通道不会越权成为任务调度通道。
23. 作为服务维护者，我希望未来可替换 SMTP 或其他邮件发送适配器，以便测试不依赖真实邮箱和外部网络。
24. 作为测试维护者，我希望通过认证后的 MCP 工具验证外部行为，以便测试不依赖私有表访问或具体 SMTP 实现。

## Implementation Decisions

- `email-service` 是 `centre-control` 下独立的 Python 子项目，使用 Python 标准库、uv、SQLite 和可替换的发送端口；首版不新增第三方运行时依赖。
- 对外唯一写入口是受鉴权的 MCP 工具 `send_notification`；另提供只读 `get_notification_status` 和健康检查 `health`。`send_notification` 持久化后异步返回 `accepted_for_delivery`，不承诺邮件已发送。
- MCP 请求使用统一 `human_notification_intent` 封套，至少包含：`notification_id`、`dedupe_key`、`notification_kind`、`recipients`、`subject`、`body`、`related`、`schema_version`。
- `body` 支持受限的 `text/plain`；首版不接受任意 HTML、脚本或附件。主题、正文长度和字符集由服务端校验。
- `recipients` 优先使用 `principal_id`，由 Registry 的只读联系人接口解析邮箱；email-service 通过 `RecipientResolver` 端口隔离具体传输和存储，不能直连 Registry 数据库。联系人缺失、禁用或地址不一致时记录不可重试错误。
- 统一公共邮箱的 From 地址、SMTP 地址、账号和凭据只由 email-service 的 `.env` 提供；调用方不能传入 From、SMTP 或凭据字段。
- HTTP `GET /health` 提供最小健康探针；MCP `health` 提供认证后的分项状态。健康状态至少区分 `ready`、`degraded`、`not_configured`、`unavailable`，不返回凭据、正文或内部堆栈。
- `notification_kind` 采用开放但受服务端配置约束的字符串；首版至少覆盖：`draft_ready`、`execution_question`、`execution_failed`、`revision_draft_ready`、`revision_failed`、`prereview_completed`、`candidate_revision_requested`、`candidate_rejected`、`workflow_binding_required`、`workflow_load_failed`、`workflow_start_failed`、`agent_unavailable`、`task_terminal_summary`。
- `related` 只保存稳定弱引用，例如 `mapping_domain_id`、`task_node_version_ref`、`candidate_id`、`candidate_head`、`formal_revision_id`、`pending_handoff_id`、`execution_id`；邮件服务不解释这些引用并据此修改业务状态。
- 投递状态为 `pending`、`sending`、`sent`、`retryable`、`permanent_failure`、`invalid`。`pending/sending/retryable` 可恢复；`sent` 为成功终态；`permanent_failure/invalid` 为不自动重试终态。
- 相同 `dedupe_key` 且请求内容相同或等价时返回既有记录，不重复发送；相同 `dedupe_key` 但主题、正文、收件人或通知类型不一致时返回 `idempotency_conflict`。
- 暂时网络、SMTP 服务不可用和超时进入 `retryable`；地址无效、schema 不兼容、缺少必填字段、内容违反限制进入 `permanent_failure` 或 `invalid`；重试使用持久化记录和退避策略，具体时间参数由实现票确定。
- 进程启动时扫描 `pending`、超时 `sending` 和 `retryable` 记录；恢复必须复用原 `dedupe_key`，不重新生成通知事实。永久失败保留查询记录，并可由运维入口或人工操作重新提交新的 `notification_id`。
- 统一调用账本记录 `caller_id`、`caller_type`、服务、工具、通知目标、结果、错误码和耗时；投递表记录 `notification_id`、状态、尝试次数和错误摘要；两者职责分开。
- 邮件发送成功只表示通知投递成功；邮件失败只改变通知投递状态，不回滚正式 Map、候选、PendingHandoff、Task Agent 执行记录，也不发布或撤销任务交接。
- 发送适配器通过进程内端口隔离，单元测试使用 Fake；真实 SMTP、第三方邮件 API、Redpanda 适配器、邮件模板平台和附件上传不属于首版。
- `shared/audit-trail` 只记录 MCP 访问账本；email-service 自己的 delivery store 是 `get_notification_status` 的权威来源。两者不双写同一业务状态、不互相替代，只通过 `notification_id` 弱关联。
- 首版提供 `send_notification`、`get_notification_status` 和 `health`：前两者要求认证；HTTP `GET /health` 允许最小未认证探针，只返回 `status`、服务名和 API 版本；认证 MCP health 返回分项状态。
- `get_notification_status` 只查询 email-service 自己的 delivery store；普通调用方只能查询自己提交的通知，运维身份按授权范围查询；不返回完整正文、原始 SMTP 错误、堆栈或凭据。
- `notification_kind` 使用固定核心类型加服务端配置允许的命名空间扩展；未配置类型拒绝，扩展类型不能改变业务状态，并按调用方能力限制。
- `send_notification` 持久化成功后异步返回 `accepted_for_delivery`；后台 dispatcher 负责发送和 retryable 重试。持久化失败返回 `storage_unavailable`，不发送邮件。
- 首版不提供普通调用方的 `retry_notification`；后台自动重试 retryable，人工重新发送必须创建新的 `notification_id`。
- MCP 传输使用官方 Python `mcp` SDK 的 Streamable HTTP，与 Registry 相同；「不新增第三方运行时依赖」只排除 SMTP、邮件 API 和队列客户端，不排除这个已经选定的 MCP SDK。

## Testing Decisions

- 最高测试接缝是认证后的 MCP `send_notification` 调用，验证输入校验、权限拒绝、幂等返回、状态结果和稳定错误码；不测试私有 SQLite 表访问顺序或具体 SMTP 库。
- 使用临时 SQLite 和 Fake sender 验证成功发送、重复发送、幂等冲突、暂时失败、永久失败、非法 payload、进程重启恢复和发送结果未知。
- 使用独立 delivery store 验证 `get_notification_status` 读取投递状态；使用共享调用账本验证调用者和 MCP 工具留痕，两个查询面不混用。
- 验证 `principal_id` 解析成功、联系人缺失、调用方提供的邮箱与登记不一致，以及调用方尝试自定义 From/SMTP/凭据时被拒绝。
- 验证不同 `notification_kind` 的最小关联字段、主题正文限制、敏感字段拒绝和不产生业务状态变更。
- 验证邮件服务不可用或发送失败时，外部领域事实不被回滚，且任务消息通道不受影响。
- 使用仓库已有 Python 子项目的 uv、pytest、compileall 和临时资源验证习惯；不依赖真实邮箱、真实 SMTP、真实 Redpanda、固定端口或真实凭据。

## Out of Scope

- 通过 Redpanda `notification-intent` topic 直接消费通知；首版 MCP 是唯一输入入口。
- 邮件回复驱动 PO 决策、候选正式化、返修、任务分派或任何领域状态变更。
- 由 email-service 判断执行是否失败、依赖是否满足、是否存在后继 TaskNode 或是否应发布 `task_handoff_ready`。
- 真实 SMTP/第三方邮件 SDK 的选型、生产凭据配置、邮件服务部署编排和高可用方案。
- 任意 HTML、脚本、附件、模板市场、批量营销邮件和复杂收件人规则。
- 修改 Research Mapping、LLM-Wiki、Registry、PendingHandoff 或 Task Agent 的领域事实。
- 真实 Registry MCP 适配器。首版 `RecipientResolver` 使用 Fake；Registry 实现完成后另接，不阻塞本规格的实现票。

## Resolution

本票规格已收敛。邮件服务首版以受鉴权 MCP 为唯一输入入口，使用 Registry 只读联系人解析端口和统一公共邮箱异步发信；delivery store 是投递状态权威，`shared/audit-trail` 只记录 MCP 访问账本。HTTP 健康接口提供最小未认证探针，MCP health 提供认证后的详细状态。邮件服务不消费 Redpanda、不修改任何领域事实，`ai4-m1d1` 可按本规格进入实现。

## Further Notes

- `human_notification_intent` 是 MCP 请求和邮件投递记录的业务对象，不是首版物理队列事件。
- 发送方的业务职责由调用方决定：Task Agent 负责执行类通知，Centre Workflow 负责预审类通知，coordinator 负责交接等待和终点通知；email-service 只负责投递。
- 该规格完成后，`实现 email-service 通知意图投递与重试` 才可进入实现；当前工作区中的 email-service 代码只能作为未审草稿，必须按本规格重构或删除。
