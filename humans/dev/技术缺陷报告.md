## B1. 共享库 `audit_trail` SQLite 跨线程编程错误（高）

**现象**：wiki 候选提交（`submit_candidate`）返回 `{"code":"audit_unavailable"}`；wiki-mcp stderr：
```
could not record attempted audit call: SQLite objects created in a thread can only be
used in that same thread. The object was created in thread id ... and this is thread id ...
```
此前 mapping 侧也出现过同源报错（`audit_unavailable`）。

**复现**：wiki-mcp（ThreadingHTTPServer）处理一次需写审计日志的调用（如 submit_candidate）即触发。

**根因**：venv 内安装的 `audit_trail` 包是**旧版**：`open_connection()` 用 `sqlite3.connect(path)` 未加 `check_same_thread=False`。而 MCP 服务用多线程 HTTP 服务器，审计连接在启动线程创建、被工作线程使用 → sqlite3 抛 `ProgrammingError`。

**定位**：
- `research-map/.venv/Lib/site-packages/audit_trail/__init__.py` 与 `research-wiki/.venv/...` 内 `sqlite3.connect(path)`（旧）
- 正确版本：`sci-weave/centre-control/shared/audit-trail/src/audit_trail/__init__.py:106` → `sqlite3.connect(path, check_same_thread=False)`

**修复建议**：将两处 venv 内 `audit_trail/__init__.py` 覆盖为 shared 版本（**本次已修复**，`check_same_thread=False=True`）。根治：venv 应 editable 安装 shared 包，或以 wheel 分发，避免"源码已修、venv 仍旧"的漂移。

## B2. coordinator SQLite 单连接跨线程使用，`dispatch_root_task` 崩溃（高）

**现象**：对根任务调用 `dispatch_root_task` 返回 `{"status":"dispatch_failed"}`；捕获异常为
`ProgrammingError('SQLite objects created in a thread can only be used in that same thread...')`。

**复现**：`main.py` 的 coordinator MCP 是 ThreadingHTTPServer，`dispatch_root_task` 在工作线程执行，而 SQLite 连接在启动线程创建。

**根因**：`coordinator/src/main.py:78` `sqlite3.connect(config.sqlite_path)` 未加 `check_same_thread=False`；`CoordinatorStore` 全程复用同一个 `self.conn`（轮询线程 + MCP 工作线程并发）。

**定位**：
- `coordinator/src/main.py:75-78`（连接创建，已改为 `check_same_thread=False` 并加注释）
- `coordinator/src/coordinator/store.py:94` 新增 `_LockedConnection`（`RLock` 串行化 execute/executescript/commit 等），`CoordinatorStore.__init__` 用其包装连接

**修复建议**：**本次已修复**：`connect(..., check_same_thread=False)` + `_LockedConnection` 锁代理，保证单连接跨线程安全且语句串行。回归：修复后 `dispatch_root_task` 返回 `not_dispatched/dispatched` 而非异常。

## B3. wiki 无引导首个正式版本（bootstrap）路径（高）

**现象**：wiki 数据源 `sourceStatus=unavailable`、`diagnostic: reason: no_current_pointer`、`wikiDocuments=[]`；`wiki.sqlite` 全空，`sciweave_wiki`（TerminusDB）无 schema。

**根因**：wiki 候选提交要求 `base_formal_revision_id` 必须已存在（`candidate_submission.py:103-105` 校验 `get_formal_revision` 返回基底版本），但**没有任何入口能创建第一个正式版本**——每个候选都需要基底，形成"先有鸡还是先有蛋"死结。mapping 侧有种子脚本可绕过，wiki 侧设计上缺失。

**定位**：`research-wiki/src/llm_wiki/candidate_submission.py`（基底校验）；`review.py`、`formal_query.py` 亦依赖既有正式版本。

**修复建议**：增加 `bootstrap_formal_revision`（或运维 CLI/初始化脚本），允许在没有 current pointer 时原子地写入首个正式版本（含 TerminusDB schema 初始化）。**本次以 `_wiki_e2e.py` 手工 seed 绕过**：创建 `WikiRevision`/`ResourceReference` schema + 写入 base 正式版本 + 重置 wiki.sqlite 指针。

## B4. 交接消息信封契约不一致（高）

**现象**：派发成功后，subscriber 立刻崩溃：
```
File ".../service.py", line 47, in handle_message
    task_node_id = self._required_text(target, "id")
ValueError: id is required
```
导致执行记录无法落库、`pending_handoff` 停在 `dispatched_unknown`。

**根因**：两个服务对 `task_handoff_ready` 消息结构**不一致**：
- **生产者**（coordinator）发**扁平**信封：`{message_type, mapping_domain_id, task_node_id, target_node_version_ref, target_agent_id, pending_handoff_id, trigger_revision_id}`（旧 `adapter_publisher.py`）
- **消费者**（subscriber）期望**嵌套**治理事件信封：`envelope["target"]["id"]`、`envelope["payload"]["formal_revision_id"]`、`event_id`（`service.py:45-56`）
- 该嵌套结构正是 research-map/wiki/gateway-ingest 统一使用的 `{event_id, target:{kind,id}, payload:{...}}`。

**定位**：
- 生产端：`coordinator/src/coordinator/adapter_publisher.py`（`publish()` 组装 `envelope`，已改为嵌套结构，含 `event_id`/`target`/`payload`）
- 消费端：`centre-agents/gateway/subscriber/src/gateway_subscriber/service.py:46-47`

**修复建议**：**本次已修复**生产端改为统一嵌套信封。根治：把信封 schema 收敛到 `shared/message-envelope`（项目里已有该包并定义了 `task_completed` 等 payload），生产/消费双方都从该模型序列化/校验，避免再次漂移。

## B5. subscriber 单条坏消息崩溃整个消费循环（高）

**现象**：一条格式不符的消息令 subscriber 进程抛出未捕获异常退出；此后所有交接都不再处理（直到进程被重新拉起，且重启又因 `auto.offset.reset=earliest` 重放该坏消息再次崩溃，形成**崩溃循环**）。

**根因**：`cli.py run_loop` 的 `for message in batch:` 内 `service.handle_message(message)` 未做 try/except，异常直接冒出 `main()`。

**定位**：`centre-agents/gateway/subscriber/src/gateway_subscriber/cli.py:106`（已加 `except Exception` 隔离 + 告警日志）
- 相关：`gateway_subscriber/queue.py:84` `auto_offset_reset="earliest"`（新组从最早重放，放大坏消息影响）

**修复建议**：**本次已修复**：单条消息异常 → 记录 `skipping unprocessable queue message topic=... offset=...: <err>` 并 commit 跳过（poison-pill 隔离）。生产建议补死信队列（DLQ）而非静默跳过；并考虑 `auto_offset_reset="latest"` 或带容错的重放策略。

## B6. 缺少 `task_completed` 生产者（高，架构缺失）

**现象**：worker 执行完成后，`execution_records=completed`，但协调器 `completed_fact` 表恒空、下游 T2… 永远 `blocking_dependency_missing`。**看板 `completed` 恒为 0、任务恒 `unknown`**（叠加 B7）。

**根因**：协调器**已实现消费** `task_completed` 事件（`adapter_events.py:54、71-98` → `service.on_task_completed` → 写 `completed_fact` + `_recompute_downstream`），但**整个 centre-agents 里没有任何组件发布 `task_completed`**（全项目 grep 无生产者）。即"完成回写闭环"只做了消费端、没做生产端。

**定位**：
- 消费端（存在）：`coordinator/src/coordinator/adapter_events.py:71` `_handle_task_completed`；`coordinator/src/coordinator/service.py:131` `on_task_completed`
- 生产端（缺失）：`centre-agents/gateway/subscriber/src/gateway_subscriber/`（worker 完成处 `worker_runner.py:131-135`、`cli.py run_loop` 均未发事件）

**修复建议**：在 subscriber 的 worker 完成分支（`worker_runner.py`）新增"发 `task_completed` 到 `sciweave.governance-events`（message_type/payload 用 `shared/message-envelope` 的 `task_completed` 模型：`task_node_id`、`node_version_ref`、`formal_revision_id`、`mapping_domain_id`）"。**本次以 `_publish_completed.py` 手工向 Kafka 发布 `task_completed` 验证消费端**：`completed_fact` 落库、T2 由 `blocking_dependency_missing`→`waiting`，证明消费端逻辑正确、纯缺生产端。

## B7. 任务执行状态无回写映射，看板任务状态恒 `unknown`（高，结构性）

**现象**：mapping 看板任务列表 5 个任务 `status` 恒为 `unknown`，`completed` 计数恒 0，即便执行已完成、`completed_fact` 已落库。

**根因**：mapping 看板源的**唯一**状态来源是**映射节点文档自身的字段** `execution_status / task_status / status`（缺省 `unknown`）。而执行状态实际存放在 **centre-agents 的 `execution_records` 表** 与 **协调器 `completed_fact` 表**；**没有任何代码把执行状态写回映射节点**（全项目仅 `dashboard_source.py:81` 读取、无写入者，测试夹具手动塞了该字段）。

**定位**：`research-map/src/research_mapping/dashboard_source.py:80-86`（`_task_status`）；写入方**缺失**。

**修复建议**：二选一：
1. 新增"执行状态投影"：协调器/网关在任务终态时，把 `execution_status` 写到对应任务节点（需扩展 mapping schema 允许该字段，并走候选/正式化或直接投影表）；
2. 让 mapping 看板源**联合查询** gateway/coordinator 的执行事实（`task_node_version_ref` 关联 `execution_records/completed_fact`），推导任务状态。
推荐方案 2（只读聚合，不改正式映射的不可变语义）。

## B8. subscriber 未配置运行时 fail-fast，令 queue 板块不可用（中，设计如此）

**现象**：queue 数据源 `查询超时`；`8761` 无监听；subscriber 启动即退出：
```
SystemExit: no Worker runtime: the DeepSeek API key is unset and the passthrough runtime
is not enabled (SCIWEAVE_GATEWAY_PASSTHROUGH_RUNTIME=1)
```

**根因**：`cli.py:50-62 build_runtime` 在 `DEEPSEEK_API_KEY` 为空且未开 passthrough 时**主动 fail-fast**（对应工单 ai4-c61f，属**有意设计**，防止静默用占位运行时）。但作为看板数据源，subscriber 不在线即整块 queue 不可用。

**定位**：`centre-agents/gateway/subscriber/src/gateway_subscriber/cli.py:37-62`

**修复建议**：这是配置问题而非代码 bug。运维二选一：配置真实 `DEEPSEEK_API_KEY`，或测试环境设 `SCIWEAVE_GATEWAY_PASSTHROUGH_RUNTIME=1`（stub 运行时，结果标注为 passthrough）。**本次采用后者**，subscriber 正常监听 8761、queue 源 `fresh`。建议看板在 subscriber 未配置时给出**明确的"未启用运行时"提示**而非笼统 `查询超时`，便于定位。

## B9. 两套栈共用 Kafka 消费组 `coordinator`（中，环境/运维）

**现象**：原生协调器已启动，但 `task_completed` 事件仍不生效；`rpk group describe coordinator` 显示 **MEMBERS 2**，事件被 docker 容器内协调器消费（写入容器内 DB），原生协调器漏收。

**根因**：Docker `sciweave-centre` 容器与原生 dev-stack **同时运行**，二者协调器都用 `bootstrap=127.0.0.1:19092`、`group=coordinator`，同一 topic 单分区 → 消费组**负载均衡**，事件被随机分给任一方。

**定位**：`coordinator` 启动配置 `SCIWEAVE_COORDINATOR_KAFKA_GROUP_ID`（原生启动脚本用 `coordinator`）。

**修复建议**：确保**只有一套栈**在运行；或测试时给原生协调器分配独立消费组（**本次改为 `coordinator-native`** 后事件全部由原生消费、下游正常激活）。根治：不同部署的消费组 id 应带环境前缀（如 `coordinator-dev`）。

## 次要发现（低）

- **B10**：`registry` `register_principal` 的 `role` 枚举不接受 `service`（返回 `invalid_role`），但 `register_workflow_agent` 的 `principal_id` 又可直接用 `service:xxx`——语义不一致。

- 备注：`main.py:85-88` 注释记录的历史缺陷（`ai4-e1jk`：`governance_kafka_bootstrap` 只读进局部变量未传给 `cls(...)`，导致治理事件恒 Noop）已在源码修复，属同类"配置未透传"隐患，建议为 `from_environment` 增加"所有字段必须显式传递"的单测。
