# 消息队列协作设计

> 状态：讨论草案，已被 `docs/data-flow/message-queue.md` 取代，并由 `.tickets/ai4-te1v.md` 承接；不构成已批准的产品规格或技术选型。本文记录 2026-10-18 的讨论，保留作历史。

## 讨论目标

为 SciWeave 的多人和多个 Agent 协作设计消息机制，重点厘清任务节点之间的通知、工作交接、阻塞和后续推进。当前仅整理讨论，不决定消息中间件、数据结构或具体实现。

## 当前讨论形成的方向

- 消息机制是多人、多 Agent 协作的核心组成部分，不只是后台任务派发工具。
- 消息围绕任务节点组织：任务节点可作为 topic（主题），下游节点可监听其前置任务节点对应的消息。
- 一个任务节点可以有多个监听者；所有监听者都应收到该任务节点发出的消息。
- 消息应通用且结构化，包含工作进度等 payload（载荷）；具体材料可通过 Wiki 或 Buffer 链接访问，不在消息中堆放大量正文。payload 的具体字段暂未决定。
- 端侧 Agent 完成工作后，通过专用 tools 和 MCP（模型上下文协议）向审核人员发送消息。审核人员使用自己的 harness（Agent 工作环境，例如 Codex）检查 Buffer 中的修改，再通过 MCP 向 Project Owner（项目负责人，PO）发送消息。
- 如果审核涉及多个 Proposal 或 Candidate branch，仍需要 Central Agent 预审；该预审不同于端侧 Agent 的工作完成通知。
- 人类接收消息后，需要完成工作并使用自己的 Codex 调用 MCP 发出后续消息，才算完成该交接；仅收到或确认通知不算完成。
- 接收者发出后续消息前处于阻塞状态；上游任务节点发出消息后解除自身阻塞。
- 若不创建新的后续任务节点，也至少向 PO 发送一条汇总结果的消息。
- 多个接收者可以各自直接向下游发送消息，不要求由原节点负责人统一汇总。

## 尚待讨论

- 多个前置任务节点的消息如何满足下游节点的启动条件：等待所有前置任务，还是按节点的依赖/激活条件决定。
- 同一任务节点是否允许发出多种消息（例如进度更新与完成交接），以及哪些消息会触发下游工作。
- 多个监听者各自工作的阻塞状态、完成条件以及分支之间的关系。
- 人类接收者未及时处理时的提醒、转交或人工解除策略；当前只确认不能把超时自动视为完成。
- 专用 MCP/tools 的职责边界，以及 Central Agent 预审如何与任务节点消息交接衔接。
- 消息 payload 的必填字段、消息版本及 Wiki/Buffer 链接表达方式。
- topic 订阅范围、订阅者变更与已发消息的接收者快照规则。
- 具体消息队列基础设施及其与产品层协作消息语义的边界。

## 与现有领域规格的关系

现有领域术语表定义了 TaskNode、Execution Record、MCP Submission、Proposal、Central Agent、TaskNode Owner 和 Project Owner，但尚未定义消息、topic 订阅或消息驱动的任务阻塞模型。本草案记录的是待进一步讨论的方向，不应被理解为已修改或取代现有首版规格。

## 暂不纳入

- 消息队列产品、协议、数据库或云服务选型。
- payload 的最终 schema、字段清单和消息状态机。
- 代码实现、依赖新增和部署方案。
- 消息队列、套件（MCP、Skills、Hooks/extensions）开发、端侧 Agent 三个新大工单的正式创建；当前仅开始梳理消息队列这一项。
