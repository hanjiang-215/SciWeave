# 中央 Agent 职责汇聚

从已有工单摘出 Centre Agent 的职责，并记录 2026-10-21 讨论后的两次收窄与 2026-10-22 的形态定稿。`centre-agents`、`buffer`、`registery` 都仍是空目录或只有说明。这里不增加新能力。

形态与进程划分见 [`work-agent.md`](work-agent.md)：Centre Agent 是 Work Agent 的中央实例，与 Task Agent 共用三组件架构。

收窄的依据与推翻条目见 `centre-agent-scope-reduction.md`。旧工单 `ai4-vbnr`、`ai4-m0vt` 描述的调度、重试、转交、推进正式版本，本文件不再采纳。

## 只做一件事

**候选版本的预审。** 只针对 Research Mapping 和 LLM-Wiki 的候选版本：做需要判断的检查，产出纳入预审报告表的结论与冲突矩阵，必要时生成混合候选。不审核 Task Agent 的设计。

工单里的中央 Agent 是一个 Agent，配置两套互相隔离的管理 MCP。它不通过一次提交同时改两个领域。

> 修订（2026-10-21）：原第一件事「部署 Task Agent」已删去。Task Agent 改由研究员端侧自持，中央不再部署、绑定或审核 agent 设计。依据工单「Task Agent 改由研究员端侧自持」。中央 Agent 由「做两件事」变为「只做一件事」。

## 预审产物与门禁（2026-10-21 第五轮）

本节的裁决来自用户逐条确认，取代上文按「格式、引用、权限、依赖、基准版本、冲突、影响范围」七项平铺的表述。

| 主题 | 结论 | 工单 |
| --- | --- | --- |
| 报告存储 | 只追加日志写入领域治理记录，唯一键 `(candidate_id, candidate_head, rule_set_version)`，重复审同一 head 返回首次结论 | ai4-oz3s |
| 写权限 | 两个独立工具：`append_prereview_log` 与 `create_merged_candidate`，可选不同的凭据 | ai4-oz3s |
| 机械检查 | 格式、对象引用、依赖环前移到领域 MCP 创建候选时拒绝；中央 Agent 只做权限范围、对象冲突、影响范围、混合 | ai4-eex0 |
| 纳入范围 | 所有未放弃、未正式化、未被驳回的候选，不按基准版本过滤；`stale` 只是报告里的一列 | ai4-a2ba |
| 触发 | 领域 MCP 在候选创建与 head 更新时自动发事件，短窗口去抖；收到信号后拉全量候选做一次快照审 | ai4-a2ba |
| 门禁 | 硬门禁，粒度是单候选：有报告的能批，缺报告的卡住；不做整链冻结 | ai4-a2ba |
| 故障 | 中央服务不可用时阻塞并排查，不放行、不降级；待审候选的卡点必须对 PO 可见 | ai4-a2ba |
| 混合候选 | 保留。只能新建分支，作者记为全部来源作者且来源作者无操作权，不可二次混合 | ai4-8dgd |
| 注册 | 进注册表，`kind = centre`，所属主体留空；只留痕，不参与鉴权 | ai4-t2wc |
| 能力范围 | 只保留预审一类职能，不接受其他能力 | ai4-rlv6 |

**能力清单会被慢慢加项，产物清单不会。** 因此边界不表述为「允许哪些工具」，而表述为「唯一产物是预审报告与混合候选」。读全部活动候选、写报告、发结论通知都属于预审本身，不算新增能力。

一条明确排除在能力之外的：**中央 Agent 不判断「下一步该谁动」**。它只产出报告与冲突矩阵，PO 决定批准或打回，提交者决定是否出新候选。硬门禁加上「它还能指挥下一步」就成了变相调度，会重新生成已被删掉的调度职责。

## 报告的失效与重算（2026-10-22）

预审报告只在它所依据的两个时点仍然成立时有效：报告的 `candidate_head` 与 `base_formal_revision_id`。任一移动，旧报告即失效。

| 触发 | 处置 |
| --- | --- |
| 候选头变化 | 领域 MCP 发候选事件；新 head 产生新报告条目，并追加一条 `head_moved` 失效判定指向新报告 |
| 正式版本发布（PO 推进） | 领域 MCP 发正式版本事件；受影响候选追加一条 `base_moved` 失效判定，并在下一次预审时重算 |

**失效用追加判定表达，不改旧报告。** 判定表按候选追加、只追加，报告行一个字不动；「当前有效报告」由同一候选最新的那条判定推出。这一点是契约细节，见「预审报告的追加日志契约」(ai4-oz3s)。

**失效不等于放行，也不等于冻结全体。** 被失效判定命中的候选在重算完成前处于卡住状态——硬门禁不变，粒度仍是单候选。没受这次正式版本影响的候选照常可批。

失效状态由领域治理记录承载（`ai4-oz3s` 的追加日志），不靠 PO 手动通知，也不做定时轮询：正式版本发布本身就是一条事件，与候选事件走同一条订阅路径。

## 不能做的事

- 不代替 TaskNode Owner 审阅草稿，也不代替他把草稿转成候选分支。
- 不代替 Project Owner 批准正式路线、目标、依赖、激活条件、回滚或恢复。
- 不把候选、或仅被节点负责人接纳但尚未正式发布的内容送去调度。
- 不把 Mapping 和 Wiki 写进同一次提交或同一个 Proposal。
- 不替 Project Owner 在多个候选方案里做最终选择。
- 不部署、不安装、不重启、不托管研究员的 Task Agent，也不保存其模型凭据。
- 不写审计。留痕由中央 MCP 接口层统一记录对外调用；领域治理记录由领域服务自己写，中央 Agent 无私有审计通道。
- 不判断「下一步该谁动」。只产出报告与冲突矩阵，由 PO 与提交者各自决定处置。
- 不写正式版本，不改写已有候选，不写草稿箱的接纳或驳回状态。

## 开发顺序

1. 先落三个组件的骨架：`gateway/mcp`（处置面）、`gateway/subscriber`（候选与正式版本事件）、`worker`（一轮预审）。
2. 领域 MCP 先补齐写入时的机械校验与候选读接口，Centre Agent 才有干净的输入与读取入口。
3. 从两套管理 MCP 读同一时点的全部可送审候选做快照预审，写只追加的预审报告。
4. 对语义上兼容且需要合并的候选，新建混合候选分支，交 Project Owner 选择。
5. 不写正式版本，也不发起执行。

## 开发形态

已定的部分：`centre-agents` 是 `centre-control` 下的独立项目，一个 Agent，对外只通过两套互相隔离的管理 MCP 谈 Mapping 和 Wiki，自己不保存领域正文。

运行时（2026-10-22 定稿，见 [`work-agent.md`](work-agent.md)）：中央 Agent 是 Work Agent 的中央实例，与 Task Agent 共用同一架构——`gateway/mcp`（处置面）、`gateway/subscriber`（消息监听）、`worker`（一轮 loop 结束即退出）三个组件，加一份本地 SQLite 与 Worker Lease。单实例常驻，不按任务类型复制多份 Agent；能力差异用 MCP 工具区分，不用多个实例区分。

与 Task Agent 的三处差异只有：订阅候选事件与正式版本发布事件而非 `task_node_id`；一轮 loop 做全量候选快照预审；处置面承接候选与报告的处置而非返修。处置面工具名与签名与 Task Agent 一致，但当前不提供功能，返回 `unimplemented`——中央 Agent 的工作里没有返修。

> 修订（2026-10-21）：原「复用 `sci-weave/task-agent` 的 Gateway 代码，让同一组件组同时承担 MCP 入口和消息队列消费」作废。Task Agent 的 Gateway 已移到研究员端侧，与中央 Agent 分属不同部署单元、不同项目组。中央 Agent 如需进程骨架与审计写法，按需自建，不复用端侧代码。

需要注意的边界：Centre Agent 的处置面 MCP 与 Task Agent 同名同签名，但当前不提供功能（返回 `unimplemented`）。它不对外暴露任何能创建执行或下发任务的工具。

> 修订（2026-10-21，第五轮）：原「不承担消息队列消费」作废。预审由候选事件触发（见 `ai4-a2ba`），因此中央 Agent **必须**消费消息队列：它主动出站连接中央队列订阅候选事件，不对外提供入站可达地址。这仍属「不对外暴露」的范畴——订阅是出站连接，不是新入口。
