# Web 看板与平台状态可见性设计

- 日期：2026-10-22
- 对应工单：`ai4-6v70`
- 状态：已收敛，可进入实现规划
- 适用对象：研究人员、Project Owner、中央 Agent 运维人员和首次使用平台的协作者

## 1. 目标与边界

Web 看板是 SciWeave 的只读观察层，用来回答三个问题：

1. 当前有哪些研究任务、研究图和 Wiki 内容正在推进？
2. 哪些工作已完成、正在等待、被阻塞或发生失败？
3. 失败或等待是否与消息监听服务、领域服务或人工处置有关？

首版看板不成为第二套正式写入入口，不直接创建、编辑、审核、发布、取消或重试任何领域对象和服务配置。看板可以提供“去哪里处理”的上下文链接或操作提示，但具体动作必须由授权人员通过 Gateway MCP 完成，或由领域 Agent 通过 Research Mapping、LLM-Wiki、Buffer 等领域 MCP 完成。

看板不自动判断 MCP 调用失败的根因，不把网络抖动、权限问题、参数错误、业务拒绝和服务故障混成一种状态；它只展示可验证的失败事实和证据。

## 2. 用户与最小使用路径

### 2.1 研究人员

打开首页后先看自己关注的任务和最近变化，进入任务详情查看当前节点、前置节点、等待原因、关联 Proposal/Wiki 版本和最近事件。研究人员需要在不理解内部服务名称的情况下知道“现在发生了什么”和“下一步应找谁处理”。

### 2.2 Project Owner

从项目总览定位路线阻塞、候选审核等待、正式版本发布结果和执行失败。详情页必须显示关联的消息事件、Gateway 处置记录和精确的执行标识，便于 Owner 在自己的 harness 中完成处置。

### 2.3 中央 Agent 运维人员

查看消息监听服务是否仍在上报状态、最近一次成功检查时间、订阅范围、消费者组和最近错误摘要。看板展示事实，不自动重启服务、不自动补发消息、不自动重试执行。

### 2.4 首次使用者

页面使用业务语言为主，内部标识作为可展开的诊断信息；每个状态必须有文字说明，不能只用颜色、图标或缩写表达。

## 3. 信息架构

首版包含四个只读视图：

### 3.1 项目总览

展示：

- 项目名称、更新时间和数据完整性提示；
- 研究路线总体进度：已完成、进行中、等待、阻塞、失败的 TaskNode 数量；
- 最近变化时间线：正式版本发布、候选变化、任务接收、执行完成、处置失败；
- 需要关注的项目：阻塞、失败、数据过期或服务状态未知的项目；
- Task Agent 和 Centre Agent 消息监听服务摘要。

总览只做聚合，不隐藏异常。聚合数字必须能进入对应的过滤结果列表。

### 3.2 路线与 TaskNode

展示 Research Mapping 的正式路线、TaskNode、DependencyEdge 和每个节点的状态。候选分支和正式版本必须明确区分：候选内容可以作为“待审核变化”展示，但不能被显示为当前正式路线。

每个节点至少显示：节点名称、状态、负责人/执行主体、前置节点完成情况、当前正式版本标识、最近事件时间、阻塞原因和关联执行记录。

### 3.3 Wiki 与候选变化

展示当前正式 Wiki 版本、候选 Proposal、候选 head、审阅状态、引用资源资格和正式化结果。资源引用必须显示精确 ResourceVersion 标识及其资格状态；不允许为了方便而替换成“当前最新版本”。

候选、待审、被拒绝、撤回和已正式化内容使用不同状态和说明。候选内容不进入正式内容列表。

### 3.4 执行与服务状态

展示 Task Agent/Centre Agent 的执行记录、消息事件和外围监听服务状态。执行详情显示触发来源是消息还是人工处置，消息主题/分区/offset 等队列诊断信息放在“诊断详情”折叠区。

服务状态显示每个监听器的名称、最近一次成功心跳/检查时间、检查周期或数据来源、订阅目标、最近错误事实和状态新鲜度。A2A 健康检测不纳入首版。

## 4. 统一状态语义

所有状态必须同时有机器值、中文名称、解释和最近更新时间。推荐的展示分组如下：

| 分组 | 状态 | 含义 |
| --- | --- | --- |
| 进度 | `queued` | 已有可处理事件，尚未开始执行 |
| 进度 | `running` | 已接纳并正在执行 |
| 进度 | `waiting` | 等待人工回答、审核或其他明确输入 |
| 进度 | `succeeded` | 本次执行已完成且结果可读取 |
| 处置 | `revision_required` | 已要求返修，等待新的处理尝试 |
| 处置 | `cancelled` | 已由授权人员取消 |
| 结果 | `failed` | 已确认失败，存在明确失败记录 |
| 结果 | `result_unknown` | 无法确认远端操作是否成功，必须对账，不得显示为成功 |
| 数据 | `stale` | 数据超过允许的新鲜度，当前显示不能代表实时状态 |
| 数据 | `unavailable` | 查询目标不可读或返回不可用 |
| 数据 | `partial` | 页面只拿到部分来源数据，聚合结论不完整 |

`blocked` 不作为执行记录的泛化状态。TaskNode 的阻塞应由可读的阻塞原因组成：等待前置节点、等待人工审核、等待资源资格、等待服务可用性、返修中或数据不可用。消息已到达即表示上游发布事件存在，看板不重复推断“上游是否就绪”。

## 5. 阻塞、失败与数据新鲜度

### 5.1 阻塞卡片

每个阻塞项必须显示：对象类型和 ID、阻塞类别、直接原因、发生时间、最近变化时间、责任主体（如已知）、关联 TaskNode/Proposal/Execution ID，以及建议通过哪一类通道处理。建议只写事实，例如“等待 Project Owner 审核”，不写“系统卡住”这类未经证实的判断。

### 5.2 MCP 失败

MCP 调用失败卡片必须显示：调用目标、工具名、调用时间、调用身份或主体（可脱敏）、关联执行记录、返回的失败摘要和请求/幂等标识（若可用）。平台不自动分类根因，也不自动重试。用户可复制诊断标识，在 Codex、Cursor 或其他授权 harness 中重现或处置。

### 5.3 消息失败与重复

消息事件显示消息类型、业务幂等键、发布时间、接收时间、消费者组、处理结果和 offset 证据。至少一次投递造成的重复事件要标记为重复观察，不把重复本身当成新的业务执行成功。看板不改变 offset，不补发消息。

### 5.4 新鲜度

每个数据来源返回 `observed_at`、`source_status` 和可选的 `fresh_until`。页面顶部和来源卡片显示“数据更新时间”。超过来源声明的新鲜度窗口时显示“数据可能过期”，但不凭空生成统一秒数；没有新鲜度信息的来源显示“新鲜度未知”。

## 6. 读取边界与数据流

看板使用只读查询适配器从各自领域的查询面读取：

- Research Mapping：正式路线、TaskNode、DependencyEdge、候选审阅事实和正式化结果；
- LLM-Wiki：正式 Wiki 版本、Proposal、资源引用资格和正式化结果；
- Buffer/治理：候选、审核、批准、拒绝和审计索引；
- Gateway：执行状态、人工处置记录、MCP 调用结果和关联审计；
- 消息监听器：最近检查时间、订阅目标、消费者组、消息处理结果和错误事实。

看板不直接读取各服务的私有 SQLite 文件、TerminusDB 内部结构、运行时会话文件或队列 offset 存储。各服务应提供稳定的只读查询契约；前端通过一个看板查询层获取统一的展示模型，避免浏览器同时理解多个领域存储。

查询层必须保留来源标识和对象版本，聚合失败时返回部分结果及来源错误，而不是用空数组掩盖不可用。对正式内容，查询层遵循领域服务的正式查询规则：候选、未审批内容、未激活 Commit 和跨存储不一致结果不得伪装成正式数据。

## 7. 交互与可用性要求

- 默认按“需要关注”排序：阻塞、失败、结果未知、数据过期优先；支持按项目、状态、负责人、时间范围和对象类型筛选。
- 列表保留稳定 URL 查询条件，用户可以复制链接给协作者定位同一上下文。
- 详情页提供面包屑、返回列表和关联对象链接，避免用户只能从首页重新寻找。
- 状态颜色必须配合文字、图标和可访问名称；颜色不能是唯一信息载体。
- 适配窄屏：核心状态、对象名称和处理建议优先，诊断字段折叠；不要求首版提供原生移动端安装能力。
- 所有时间同时显示相对时间和可展开的 UTC 时间；相对时间更新不能改变原始时间。
- 加载、空数据、部分数据、数据过期、查询失败分别展示；空数据不等于查询失败。
- 不自动刷新到打断用户阅读的位置。提供手动刷新和可控的自动刷新开关；刷新失败保留上一次数据并明确标注其时间。
- 把内部术语放入帮助文本，例如解释 Proposal、TaskNode、消费者组和结果未知；不要求用户先阅读开发文档。

## 8. 错误处理与安全边界

看板应采用最小权限的只读访问身份。认证、授权、脱敏和审计由看板后端或部署边界处理；令牌、路径、端口和服务地址通过环境变量配置，不写入前端源码。

查询超时、来源不可达、权限拒绝、响应格式错误和数据不一致在统一错误模型中保留来源、时间、请求标识和可安全展示的摘要。敏感参数和令牌不得进入浏览器日志、复制按钮或错误详情。

当多个来源无法在同一时刻一致读取时，页面显示各来源的观测时间和“部分数据”，不拼接成看似完整的状态。看板本身宕机不应改变任何领域数据、消息或执行状态。

## 9. 实现拆分建议

当前工单完成领域规格，不指定具体 Vue 版本、构建工具、状态管理、组件库、后端框架或部署方式。进入实现前应新建独立实现工单，并在其中确定：

1. Vue 子项目目录、包管理器、构建与测试工具，并提交自身清单和锁文件；
2. 看板查询层的接口契约和各来源适配器；
3. 最小可用的四个视图及其测试数据；
4. 认证、脱敏、审计和部署配置；
5. 端到端验证，包括部分来源失败、结果未知、重复消息、数据过期和只读边界。

不在实现票确定前新增第三方依赖，不把领域服务的私有存储直接暴露给浏览器。

## 10. 验收映射

- 展示对象：项目总览、Research Mapping、LLM-Wiki、TaskNode、执行记录、消息事件和监听服务状态已定义。
- 状态与阻塞：统一状态、阻塞类别、失败、结果未知、数据不可用和新鲜度语义已定义。
- 监听服务：最小状态字段、订阅诊断信息、错误事实和 A2A 排除范围已定义。
- 写入边界：看板只读；消息队列负责任务流转；Gateway MCP 负责人工处置；领域 MCP 负责 Agent 工作；看板不改变任何写入状态。
- 实用性：面向研究人员、Project Owner、运维人员和首次使用者，提供关注排序、稳定链接、可访问状态表达、部分失败保留和可复制诊断上下文。
