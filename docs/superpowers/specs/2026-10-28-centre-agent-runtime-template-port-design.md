# 中央 Agent 运行时按 Task Agent 模板补齐

- 状态：施工前规格，供拆票使用

## Problem Statement

中央 Agent 的职责只有一件：对 Research Mapping 与 LLM-Wiki 的候选做预审，把结论追加进领域治理日志，必要时生成混合候选。它的三个组件（处置面、消息监听、短生命周期 Worker）都已经在仓库里，代码也在，但**这条链上没有一处真正把工具递到模型手里，也没有一处真正把一轮 loop 拉起来**。

具体地，三处断链叠在一起：

1. **触发面为零。** 治理事件消费器算出一个 `recompute_triggered` 计数，然后把它打进日志字段，没有别的读者。没有代码写执行记录，没有代码拉起 Worker。也就是说：候选被创建、被更新、正式版本被发布，中央侧判定「该重算了」，然后什么也没发生。
2. **工具面为零。** Worker 起 fast-agent 时没有声明任何 MCP server，生成的 `fast-agent.yaml` 只有 `compaction` 和 `session_history` 两行。模型手里一个工具都没有，读不到候选，也写不了预审结论。它唯一能做的事是照着一句「把负责人的命令简洁地完成」编一段话。
3. **卡片是死的。** 中央套件里六张 MCP 卡片已经按 capability 写好并收窄过（含 `list_reviewable_candidates`、`append_prereview_log`、`create_merged_candidate`），但中央侧源码一次都没读过它们；而且安装脚本只拷 `bin` / `cron` / `systemd` / `README.md`，**卡片目录和套件清单压根没被装进去**。套件自检也不检查它们。

后果是：投给中央 Agent 的候选永远得不到预审结论。`docs/data-flow/centre-agent.md` 写的「事件触发 → 拉全量快照 → 追加预审日志」这条链，目前只有中间一段。

同时还有一处稳定性缺陷：Worker 租约表只有 `acquired_at`，没有过期时间，读取侧只判断「有没有这一行」。一次 Worker 崩溃（或订阅器被 kill）之后，那个目标就永远拿不到租约，永远跑不动了。

## Solution

把 Task Agent 套件里已经验证过的五个接缝搬到中央侧，让预审这条链从「事件」通到「工具调用」：

- **执行记录先落库。** 治理事件消费到需要重算时，先在一个本地事务里写一条执行记录（状态 `queued`），再交出执行权。落库成功才提交 consumer offset；落库失败则不提交，消息重放。
- **Worker 是独立子进程。** 订阅侧用显式的执行标识拉起一个短生命周期进程，进程退出即一轮结束。不再在订阅器进程里内联跑模型，也不再用 `multiprocessing` 把一个运行时对象 pickle 过去。
- **工具面从卡片来。** Worker 启动时读中央套件的 MCP 卡片，按 Agent 定义里声明的允许资源生成 `mcp.servers` 块，缺环境变量就硬失败。模型第一次真的能调 `list_reviewable_candidates` 和 `append_prereview_log`。
- **Agent 定义可加载。** 预审指令从一份 YAML 定义来，不再是一行硬编码字符串；`allowed_mcp_resources` 决定这个 Agent 拿到哪几张卡。
- **租约带过期。** 领取租约写入 `expires_at`，过期即可被下一次派发回收；正常结束或失败时删除。

搬的是**接缝的形状**，不是把套件的运行时包搬过来：按 ADR-0002，两侧源码保持分开，中央侧自己实现这几个模块。

## User Stories

1. 作为 Project Owner，我想在候选被创建后不久就看到一条中央预审结论落进领域治理日志，这样我不必手工确认「中央 Agent 是不是还活着」。
2. 作为 Project Owner，我想在正式版本发布后让受影响的候选自动进入重算，这样基于旧基准的预审结论不会继续冒充当前结论。
3. 作为 Project Owner，我想在一个候选卡住时看到它的执行记录停在哪个状态，这样我能区分「在排队」「在跑」「失败了」。
4. 作为 Project Owner，我想在中央 Worker 崩溃后不必手工删数据库里的行就能让它重新跑，这样一次意外不会让某个候选永久失效。
5. 作为运维者，我想在处置面上直接看到最近一次预审的执行记录与错误码，这样排查不必去翻日志。
6. 作为运维者，我想在环境变量缺失时让 Worker 在启动阶段就失败并说明缺哪一项，而不是启动成功、跑完一轮、产出一段没有工具痕迹的文字。
7. 作为运维者，我想让套件安装完之后卡片目录真的在目标目录里，这样「装了但读不到卡」不再是可能的失败形态。
8. 作为运维者，我想让套件自检把卡片目录与套件清单算进「就绪」判定，这样安装不完整会在安装时暴露而不是在运行时报错。
9. 作为维护者，我想让预审 Agent 的指令、模型与允许资源写在一份 YAML 里，这样调整预审口径不需要改 Python。
10. 作为维护者，我想让中央侧的卡片继续按 capability 收窄，这样中央 Agent 拿不到 `formalize` 类工具，能力上限仍然由静态校验守着。
11. 作为维护者，我想在中央侧看到一份独立加载层而不是对套件的 path 依赖，这样改中央预审的启动方式不会改到研究员机器上的库。
12. 作为维护者，我想让这个加载层只覆盖真正需要的两个模块，这样两边同构的部分保持最小，漂移面可控。
13. 作为维护者，我想让「一轮 loop 干什么」由 Agent 定义表达而不是由事件里的标识符拼出来，这样模型看到的是任务而不是一个名字。
14. 作为研究员，我想让中央侧的改动完全不动我机器上的套件，这样我的 Task Agent 不会因为中央预审换了个加载方式而失效。
15. 作为评审者，我想让每一项改动都有一条只依赖外部行为的测试，这样重构实现时测试不会跟着改。
16. 作为评审者，我想在测试里看到真实子进程被启动、真实配置文件被生成，这样「没有调用方」这类缺陷不会再被 mock 掩盖。
17. 作为评审者，我想让租约过期的行为被一条确定的测试钉住，这样它不会在下次调整租约表时悄悄回退成无过期。
18. 作为评审者，我想让缺环境变量的路径被显式测到，这样「静默跳过某张卡」不会被当成可用配置。

## Implementation Decisions

### 落地位置

两个根，各自独立：

- 中央侧新代码进 `sci-weave/centre-control/centre-agents`，作为 `worker` 与 `gateway/subscriber` 之间共享的一层。`gateway/mcp` 与 `gateway/subscriber` 已经通过 uv workspace 依赖 `worker` 包（`task_agent_worker`），这一层沿用同样的依赖方式，不引入新子项目。
- 卡片与套件清单留在 `sci-weave/toolkits/centre-agent-toolkit`。中央侧**不复制卡片**，通过一个环境变量指向卡片目录。

### 不抽共享库，复制加载层（维持 ADR-0002）

按 ADR-0002 采纳的方案 3，两侧源码分开、互不 path 依赖。这次只在中央侧复制**两个模块的职责**：MCP 卡片加载与 fast-agent 配置渲染。Agent 定义加载只做到「读一份 YAML、校验允许资源」，不做套件那套四根目录、本地覆盖、未知资源报错的完整机制。

ADR-0002 的前提（「Agent 定义、MCP 卡片只有套件需要」）在这里确实松动了：中央 Agent 同样需要一份定义和一组卡片。但推翻 ADR 需要另一张票与一次单独裁决，本规格不把它夹带进来。**记录为已知债务**：两侧同为 Work Agent 实例，加载层的形状会继续收敛，届时要么抽共享包并改 ADR，要么接受长期双份。

### 触发的形状：快照审，不是按节点审

这是与 Task Agent 最重要的一处不同，必须写进实现而不是留给读者发现。

- Task Agent 的目标是 `task_node_id`，一次交接对应一个节点、一轮 loop。
- 中央 Agent 的目标是**一次全量候选快照**。消费器拿到事件后先拉全量可送审候选，再做一次覆盖全集的预审。

因此执行标识不能用单个 `candidate_id`。用（域，事件，去抖窗口）这一组来标识一次快照审，租约的目标键也用同一组。这样同一窗口内的多次候选变更合成一次预审，与 `ai4-a2ba` 定的去抖语义一致。

租约仍然是本地互斥，不是跨实例分发租约（`ai4-he04` 已裁）。

### 一轮 loop 的输入不是标识符拼出来的

中央侧的现状是把 `Execute TaskNode {id} triggered by {ref}` 这类字符串当命令文本交给模型。这正是端侧 `ai4-1e9e` 修过的那一类缺陷：把标识符当成任务。

决定：交给模型的内容是「Agent 定义里的预审指令 + 本轮的域与事件事实」，候选本身由模型通过 `list_reviewable_candidates` 自己取。指令里必须明确「你只能读候选、只能追加预审日志、不得批准任何候选」，这一条不能只靠卡片收窄来保证，因为模型会看到工具的完整描述。

### 状态机不缩窄

中央侧的执行记录状态集是 9 态，覆盖 `needs_revision` / `rejected` / `human_takeover`。套件侧的持久存储只有 6 态，那是研究员侧处置面的有意裁剪（见 `docs/data-flow/work-agent.md` 的「研究员侧处置面的当前契约」）。

**中央侧保持 9 态不动。** 这次搬的是触发、工具面与租约，不碰状态集合，也不碰处置面工具表。谁把两侧状态机对齐，方向是套件向中央靠，不是反过来。

### Worker 派发用显式子进程，不用 multiprocessing

现状是处置面用 `multiprocessing` 的 spawn 上下文把一个运行时对象当参数传过去。这在参数可 pickle 时能跑，但它把「Worker 是什么」绑在了调用方的内存布局上。

改为与端侧同形状：派发方只传执行标识与配置（命令行参数或环境变量），Worker 自己构造运行时。派发方在派发**之前**提交事务，Worker 在自己的连接上读那条记录。超时与失败由派发方判定，不由子进程自报。

### 租约写入过期时间

`worker_leases` 增加 `expires_at`，领取用 `BEGIN IMMEDIATE` 事务，判定「有效」的条件从「这一行存在」改成「这一行存在且未过期」。回收过期租约不需要单独的清扫进程：下一次派发发现过期即覆盖，并写一条审计事件。

这条与端侧行为对齐，属于 ADR-0002 说的「Worker Lease 必须两边一起改」。

### 套件安装补齐卡片

安装脚本把卡片目录与套件清单一起拷进目标目录；自检把它们算进「就绪」判定。理由是这条链上已经出现过一次「文件在仓库里、装完就没有」的形态，自检不覆盖等于没装。

## Testing Decisions

好的测试只断言外部行为：给一条治理事件，看库里多出什么；给一组环境变量，看生成的文件长什么样；给一个已过期的租约，看下一次派发能不能拿到。不断言内部函数调用顺序，不 mock 被测模块自己。

四类测试，各有先例：

1. **消费器到执行记录**。在 `CentreGovernanceConsumer.consume` 这一层断言：给一个候选事件，库里出现一条 `queued` 执行记录；去抖窗口内的第二个事件不新增记录；落库抛异常时不标记已处理。先例是现有的治理消费器测试。
2. **配置生成**。断言给定卡片与环境变量后，生成的 fast-agent 配置包含 `mcp.servers` 且每张卡的 transport 与 url 正确；缺一个必填环境变量时抛错且错误里带着变量名。先例是套件的 MCP 服务测试与运行时配置测试。
3. **真实子进程**。把 Worker 当独立进程启动，读它的退出码与标准输出。这一条必须是真的子进程，不能 mock：这次的缺陷正是「组件在、没人拉起它」，mock 会精确复现那个盲区。先例是套件的派发测试，它跑的是真实的服务模板入口。
4. **租约过期**。用可控时钟写一条已过期租约，断言第二次派发能拿到并覆盖它，且写了一条审计事件；再写一条未过期租约，断言第二次派发被拒。先例是套件的租约测试。

另外两条资产测试：安装脚本必须把卡片目录与套件清单拷进目标目录；自检必须在它们缺失时返回「不完整」。先例是套件的安装测试。

测试夹具沿用现有做法：假域 MCP 客户端、假 fast-agent 包（在 `sys.modules` 里装一个替身，检查框架收到的参数，不调真模型）。

## Out of Scope

- **混合候选的生成。** `create_merged_candidate` 在领域侧已实现，中央侧的调用时机、作者身份与不可二次混合的约束属于 `ai4-8dgd` 的范围，本规格只保证工具在卡片里可达。
- **给 Project Owner 的通知。** `prereview_completed` / `agent_unavailable` 两类通知不在这条链上，另开票。
- **处置面工具表。** 中央处置面当前只提供 6 个观察与取消工具，不扩窄也不加宽。
- **ADR-0002 的修订。** 本规格按它执行，并在「实现决定」里记录了前提松动。
- **端侧 `task_completed` 的生产者。** 那是 `ai4-lwma`。
- **真实模型与真实令牌的端到端验证。** 本机没有可用的模型密钥与领域 MCP 令牌，交付物是「接缝接上且被测试钉住」，不是「跑出真实预审报告」。这一点必须在票里写明，不要用测试通过冒充预审可用。
- **`ai4-derq` 的信封格式迁移。** 中央侧按现有信封读取（`mapping_domain_id` 与 `wiki_domain_id` 并存），不在这里改格式。

## Further Notes

- 这三处断链的病灶与 `ai4-derq` 找到的那批是同一个：组件写好了、有测试、没有生产调用方。因此每一张切片票的验收都必须包含「有一个真实调用方」，只写单测不算完成。
- 中央侧读卡片的目录通过环境变量指定，默认值指向安装后的套件目录。开发时指向仓库里的套件目录即可，两者的卡片内容应当一致——若出现分叉，是套件与运行时不一致，不是配置问题。
- 卡片的能力收窄不能被这次改动放松：`formalize_candidate` / `formalize_wiki` / `decide_wiki_review` / `record_review` 不得出现在中央侧任何一张卡里。这条已有静态校验守着，改动后必须仍然通过。
- 本机没有 `DEEPSEEK_API_KEY` 与 `SCIENCEPAL_ACCESS_TOKEN`，因此切片 3 的「模型真的调用工具」只能在有人提供密钥后补一次真实验证；在此之前该票保持「接缝已验证、真机未验证」的状态，不得标记为已实现。
