# SciWeave 演示视频脚本

> 目标：用一条可复现的科研协作链路，展示 SciWeave 如何把「中央部署、Project Owner 建项目、研究员执行、草稿接纳、候选预审、正式发布和审计追溯」串起来。
>
> 建议时长：4 分 30 秒左右。视频同时面向评审和不了解内部实现的观众，因此口播先讲科研动作，再用 MCP、消息队列和版本治理解释为什么结果可信。
>
> 重要边界：视频中应明确区分“演示数据/执行结果”“候选版本”和“正式版本”。只有 Project Owner 完成正式化之后，内容才可称为正式路线或正式知识。

## 一、视频结构总览

| 时间 | 段落 | 观众看到的结果 | 主要数据流 |
|---:|---|---|---|
| 0:00–0:25 | 开场与角色 | 明确团队协作痛点和三个主要角色 | Project Owner / Researcher / Agent |
| 0:25–0:55 | 中央服务与项目初始化 | 中央控制面和只读看板可访问 | centre-stack → Mapping/Wiki/Registry/Queue |
| 0:55–1:30 | Project Owner 建路线并分配任务 | 正式路线包含任务节点、依赖和执行者 | Owner → Research Mapping → Formal Revision |
| 1:30–2:25 | Researcher/Task Agent 执行任务 | 任务经消息交接到端侧，结果形成草稿 | Formal Revision → Redpanda → Task Agent → Draft Buffer |
| 2:25–3:25 | 草稿接纳、候选预审和 Owner 正式化 | 候选经过两层治理后进入正式版本 | Draft → Candidate → Centre Pre-Review → Owner Review → Formal |
| 3:25–4:05 | 失败恢复与版本对账 | 展示一次失败和一次安全恢复 | Execution Record / idempotency / exact version |
| 4:05–4:30 | 看板和审计收尾 | 证明结果可观察、可追溯、可解释 | Dashboard API + AuditEvent + Call Ledger |

## 二、演示前准备

### 1. 角色和窗口

准备三个窗口：

1. **Project Owner Harness**：展示 Owner 套件的 MCP 调用结果；
2. **Researcher Harness / Task Agent**：展示研究员套件、消息监听和执行结果；
3. **中央服务终端或 Web 看板**：展示正式路线、执行记录、来源状态和最终快照。

如果录制环境无法同时展示三个窗口，优先保留 Project Owner Harness 和中央服务终端；研究员侧可用已保存的执行日志和草稿结果补充。

### 2. 中央服务

确认以下服务已经启动：

- TerminusDB：保存 Research Mapping、LLM-Wiki 和 Draft Buffer 的领域数据；
- Redpanda：传递治理事件和任务交接消息；
- `sci-weave/centre-stack/`：运行 Mapping、Wiki、Draft Buffer、Registry、Coordinator、Centre Agent、Dashboard API 和 Web UI。

复用仓库自带 Redpanda 时，需要让中央容器加入 `redpanda_default` 网络，并使用容器内地址 `redpanda:9092`。生产环境使用实际可达的 Broker 广播地址，不要使用 `localhost`。

### 3. 演示数据

推荐使用一个简单的 Iris 分类研究路线：

```text
T1：固定并检查 Iris 数据快照
  ↓
T2：执行确定性 KNN 分类基线
  ↓
T3：整理结果并提交研究结论
```

演示路线中预留一个候选变更：

```text
新增 T4：分层交叉验证
```

T4 只在正式化之后进入正式 Research Mapping。若使用其他学科数据，保留同样的数据流和治理动作，不要改变演示结构。

## 三、逐段脚本

## 0:00–0:25｜开场：科研协作的问题

### 画面

- 先显示最终目标：一条研究路线、一条执行记录、一份草稿和一条正式版本变更记录；
- 再切换到 Project Owner、Researcher、Task Agent 三个角色。

### 口播

> 科研协作的难点不只是把代码跑出来，还要知道谁定义了任务、谁执行了任务、结果依据什么证据、路线为什么发生变化，以及这次变化有没有被负责人正式采纳。
>
> SciWeave 把这些动作组织成一条可追溯的数据流：Project Owner 管理正式路线，Researcher 和 Task Agent 执行任务并提交草稿，Centre Agent 预审候选，最终由 Project Owner 决定什么进入正式版本。

### 屏幕文字

```text
正式路线 → 任务交接 → 端侧执行 → 草稿 → 候选 → 预审 → Owner 正式发布
```

## 0:25–0:55｜中央服务与项目初始化

### 画面

- 展示中央服务容器和进程状态；
- 展示 Web 看板首页或 Dashboard API 返回的 live 快照；
- 展示 Registry 中已经登记的 Project Owner、Researcher 和 Task Agent。

### 口播

> 中央控制面以一个部署单元运行，里面包含两个领域服务、中央草稿箱、注册表、协调器、Centre Agent 和只读看板。TerminusDB 保存领域版本数据，Redpanda 负责传递治理事件和任务交接。
>
> 端侧套件不部署到中央容器。Project Owner 和 Researcher 分别在自己的 Harness 中使用角色套件，通过带 Bearer 令牌的 MCP 访问被授权的服务。

### 演示动作

可以展示以下只读检查：

```bash
docker compose --env-file .env exec centre supervisorctl status
curl -s http://127.0.0.1:8702/api/dashboard/snapshot
```

不要在录屏中展示 `.env`、真实令牌、SMTP 密码或模型 API Key。

## 0:55–1:30｜Project Owner 建立研究路线并分配任务

### 画面

Project Owner Harness 中依次展示：

1. `get_formal_mapping`：读取当前正式路线；
2. 路线中的 T1、T2、T3，以及节点之间的 Dependency Edge；
3. TaskNode Owner 和 `executor_refs`；
4. Registry 中对应的 Researcher 和 Task Agent 登记。

### 口播

> Project Owner 先建立研究路线。路线不是一张静态看板，而是由 TaskNode 和 Dependency Edge 组成的正式版本。每个任务有负责人、输入、输出和执行条件，自动执行的任务还会引用已经登记的 Workflow Agent。
>
> Registry 只保存主体、Agent 和运行实例的登记事实；真正决定一个任务由谁执行的是正式 Mapping 中的 `executor_refs`。这样，登记一个 Agent 不会自动获得任何任务权限。

### 关键演示点

- 强调当前读取的是 **Formal Mapping**；
- 不要把候选分支或草稿状态说成正式路线；
- 说明根任务由 Owner 显式派发，不能由任意 MCP 调用绕过路线依赖。

### 口播转场

> 路线正式发布后，Owner 再明确启动第一个根任务。后续任务不由人随意点击启动，而是由正式依赖和上游交接事件决定何时可以执行。

## 1:30–2:25｜任务交接与端侧执行

### 画面

1. Project Owner 调用 Coordinator 的 `dispatch_root_task`；
2. Redpanda 中显示或口头说明 `task_handoff_ready`；
3. Researcher 侧 Task Agent subscriber 收到自己的 Agent topic；
4. Task Agent 创建 `queued` / `running` Execution Record；
5. Worker 调用 SciPal 或本地科研工具执行 T1/T2；
6. 端侧显示执行结果、指标和证据文件。

### 口播

> 根任务由 Project Owner 显式派发。协调器会再次确认目标节点属于最新正式快照，并且没有入边。
>
> 消息队列只传递事件，不保存 TaskNode 的正式正文，也不负责决定权限。协调服务读取正式 Mapping，确认目标节点、依赖边、所需输出和激活条件都满足后，才发布 `task_handoff_ready` 到目标 Agent 的 topic。
>
> Task Agent 收到消息后，先在本机 SQLite 中写入 queued Execution Record，再领取 Worker Lease。只有成功领取租约的进程可以启动一次 Worker。这样消息重复投递时不会并行启动两轮相同任务。
>
> Worker 执行一轮科研工作，读取已授权的正式数据，调用模型、SciPal 或本地科研工具，并把执行过程和结果摘要记录在端侧。

### 数据流字幕

```text
Formal Mapping
  → formal_revision_published
  → Coordinator 检查正式依赖
  → task_handoff_ready
  → Task Agent subscriber
  → ExecutionRecord: queued → running
  → Worker Lease
  → SciPal / 科研工具
```

### Iris 演示口播

> 这里用固定的 Iris 数据快照演示。T1 核验数据来源、哈希、行数、字段和类别分布；T2 使用固定参数的 KNN 基线。参数和输入快照固定后，结果可以被重新执行和比较。

## 2:25–3:25｜草稿、候选预审和正式发布

### 画面

Researcher 或 Task Agent 执行完成后，依次展示：

1. Worker 返回 `draft_id`；
2. Draft Buffer 中出现 `mapping` 或 `wiki` 命名空间草稿；
3. TaskNode Owner 接纳或退回草稿；
4. 人通过领域 MCP 调用 `submit_candidate` 或 `submit_wiki_candidate`；
5. Centre Agent 读取候选快照并生成预审报告；
6. Project Owner 依次调用候选预览、创建合并请求、记录审核、正式化；
7. Formal Mapping 更新，新的任务节点或知识文档出现。

### 口播

> 执行完成不等于科研结论已经正式成立。Worker 首先把结果写入中央 Draft Buffer，并把 draft_id 写回 Execution Record。
>
> Draft Buffer 的一审由配置的人工审核人完成。接纳草稿只表示它可以被推进为领域候选，不表示它已经进入正式路线。
>
> 接纳后的草稿由人调用对应领域 MCP 写入候选分支。候选拥有自己的不可变 Commit、基准 Formal Revision 和候选 head。
>
> Centre Agent 从候选开始工作，而不是从原始草稿开始工作。它先核对候选快照、head 和正式基准，再检查权限范围、基准是否过期、同批候选是否冲突，以及影响范围。它只追加预审报告，不替 Project Owner 批准。
>
> 最后由 Project Owner 查看 Diff、影响范围和预审报告，按固定顺序完成候选预览、审核和正式化。只有正式化完成后，新的 Mapping Revision 才会进入正式查询和后续调度。

### 关键字幕

```text
Execution Record = 一轮执行的运行事实
Draft Buffer     = 尚未进入候选分支的草稿
Candidate Commit = 等待治理的候选版本
Pre-Review       = Centre Agent 的事实检查，不是批准
Formal Revision  = Project Owner 批准后的正式版本
```

### 推荐演示的六步调用

```text
get_formal_mapping
submit_candidate
preview_candidate
create_merge_request
record_review
formalize_candidate
```

Wiki 领域将 `record_review` / `formalize_candidate` 替换为对应的 Wiki 审核和正式化工具。

## 3:25–4:05｜失败注入：恢复数据问题，不改变正式路线

### 画面

- 使用移除目标列的 Iris 临时副本；
- T1 检查失败，显示稳定错误码 `missing_columns`；
- 展示失败的 Execution Record；
- 恢复正确快照，再次执行成功；
- 对比正式 Mapping，确认路线没有被修改。

### 口播

> 现在注入一次可观察的输入错误。T1 检查因为缺少字段而失败，只记录 Execution Record，不产生结果，也不修改正式路线。
>
> 恢复正确的数据快照后重新执行即可。这是执行故障恢复，不是研究路线变更，所以不需要创建 Proposal。
>
> 如果我们真的要新增 T4 或改变 T2 到 T3 的依赖，才需要走草稿、候选、预审和 Project Owner 正式化流程。

## 4:05–4:30｜看板与审计收尾

### 画面

- 打开只读 Web 看板的项目总览、研究路线、运行观察；
- 展示正式路线版本、执行状态、数据源状态；
- 展示一条接口调用审计记录和一条领域治理记录；
- 回到最终 Formal Mapping。

### 口播

> 最后回到只读看板。看板聚合的是已经确认的路线、执行、候选和服务状态，它不提供修改、审核、正式化或消息补发按钮。
>
> 接口层调用账本回答“谁在什么时候调用了什么工具”，领域 AuditEvent 回答“谁改变了什么治理事实”。两类记录结合起来，可以追溯一次研究结果从任务执行、草稿提交、候选审核到正式发布的完整过程。
>
> SciWeave 的核心不是让 Agent 直接修改科研事实，而是让 Agent 能够执行工作，同时让路线、证据、审核和正式发布都保持可追溯。

## 四、录制操作清单

### 录制前

- [ ] TerminusDB 已启动，三个领域库已初始化；
- [ ] Redpanda 已启动，中央容器与 Broker 使用同一个可达网络地址；
- [ ] `centre-stack` 中的关键进程状态正常；
- [ ] Project Owner 和 Researcher 套件已安装并通过 `check.sh`；
- [ ] Registry 已登记 Project Owner、Researcher、Workflow Agent 和实例；
- [ ] 正式 Mapping 已包含 T1、T2、T3；
- [ ] T1/T2 数据快照和失败注入副本已经准备；
- [ ] 演示用候选、正式基准和幂等键已记录；
- [ ] 所有真实令牌、密码和 API Key 已从录屏区域隐藏；
- [ ] 预先启动录制所需的命令窗口，避免暴露无关日志。

### 录制中

- [ ] 不展示 `.env` 和真实令牌；
- [ ] 不把 `candidate` 称为 `formal`；
- [ ] 不把 Centre Agent 的 `passed` 说成 Owner 已批准；
- [ ] 不把消息队列收到通知说成 Worker 已经执行；
- [ ] 不把 Execution Record 的 `completed` 说成科研结论已正式发布；
- [ ] 失败时保留错误码和执行记录，不要直接清空失败数据；
- [ ] 正式化后再次读取 Formal Mapping，证明指针确实发生了改变。

## 五、备用演示路径

如果真实消息队列或模型服务网络不稳定，使用以下降级路径，不要假装完成了端到端消息演示：

1. 先用已保存的真实 SciencePal T1/T2 结果展示端侧科研执行；
2. 再用真实 TerminusDB + 管理 MCP 展示 `submit_candidate → preview → review → formalize`；
3. 在画面中明确说明两段证据分别验证“端侧执行”和“平台治理”，当前录制未证明二者已经通过实时消息自动串接；
4. 用测试队列或预先保存的 Execution Record 展示状态机时，标注为测试/回放数据。

这样既能完整展示项目的核心创新，也不会把设计目标或局部证据误报为已经验证的生产闭环。

```text
SciWeave
让科研 Agent 能执行工作，也让每一次路线变化、证据提交、审核和正式发布都可追溯。

Research Mapping · Task Agent · Centre Agent · Draft Buffer · LLM-Wiki
```
